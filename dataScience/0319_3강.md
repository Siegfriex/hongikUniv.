## 2. 왜 데이터사이언스를 배워야 할까

- **T자형 인재의 필요성:** 한 분야에 깊이(│)를 갖추면서 여러 분야에 대한 폭(─)을 갖는 인재. 데이터사이언스는 그 폭과 깊이를 모두 요구하는 영역이다.
- **데이터 문해력:** 데이터를 읽고 해석하고, 숫자·시각화·모델 결과를 비판적으로 이해하는 능력. 모든 직군에서 점점 필수 역량이 되고 있다.
- **비즈니스 인사이트:** 데이터에서 끌어낸 통찰을 의사결정·제품·서비스 개선에 연결하는 능력. “무엇을 측정하고, 어떤 질문을 던질 것인가”가 성과를 좌우한다.
- **지속적 학습:** 도구·알고리즘·규제가 빠르게 바뀌므로, 한 번 배운 것으로 끝이 아니라 **계속 배우는 습관**이 필수이다.

## 3. 데이터의 분류 (수리·통계 측면)

### 데이터의 타입 (구조 관점)

데이터를 **저장·표현 구조**에 따라 나누면 **정형·반정형·비정형**으로 구분한다.

#### 정형 데이터 (Structured data)

- **정의:** **행과 열로 구성된 표**와 같이 **미리 정해 놓은 형식과 구조에 따라 저장되도록 구성된 데이터.** **고정된 필드**에 저장된 데이터를 의미하며, **관계형 DB**, **테이블** 형태, **스프레드시트** 형식으로 표현한다.
- **스키마:** 데이터를 **저장하기 전에** 미리 **구조(컬럼, 데이터 타입 등)** 를 정의해야 한다. 이렇게 정의된 구조가 **스키마(Schema)** 이다.
- **2차원 구조:** **가로 = 데이터 한 건(행, row)**, **세로 = 데이터 속성(열, column)** 이 명확히 구분되는 **2차원 구조**를 가진다.
- **타입 제약:** 각 **필드**에 들어갈 데이터가 **숫자, 날짜, 문자열** 등으로 **엄격히 제한**된다. 그래서 조회·집계·연산이 일관되고 SQL 등으로 다루기 쉽다.

#### 반정형·비정형

- **반정형 데이터 (Semi-structured):** 고정된 테이블은 아니지만 **태그·키–값·트리** 등 일정한 패턴으로 구조가 있다. 예: JSON, XML, HTML, 로그 파일.
- **비정형 데이터 (Unstructured):** **고정된 구조가 없는** 데이터. 텍스트, 이미지, 음성, 동영상 등. 전처리·추출이 필요하고, NLP·컴퓨터 비전 등으로 의미를 뽑아 쓴다.

| 타입 | 특징 | 예 |
|------|------|-----|
| **정형** | 행·열, 미리 정한 형식·구조, 스키마(컬럼·타입 사전 정의), 2차원(행=한 건, 열=속성), 필드별 타입 엄격 제한 | RDB 테이블, 스프레드시트, CSV |
| **반정형** | 테이블은 아님, 태그·키–값 등 패턴 있음 | JSON, XML, 로그 |
| **비정형** | 고정 구조 없음 | 문서, 이미지, 음성, 동영상 |

---

#### 비정형 데이터의 정형화 과정 예시: 이미지와 멀티모달

위에서 다룬 **정형 데이터**(행·열·스키마·고정 필드)가 “정수(正數)”라면, **비정형 데이터(이미지·음성·텍스트)를 그에 맞게 바꾸는 과정**이 **정형화**이다. 그 대표 예가 **이미지 → 구조화된 표현(텐서·피처·스키마 기반 출력)** 이다. 이를 **멀티모달** 관점과 **컬러 이미지의 3D 텐서 표현**, **이미지→이미지 플로우**로 개괄하고, 관련 키워드·상호관계를 정리한다. (아래 내용은 웹 자료를 반영해 보완함.)

**1. 비정형(이미지)의 정형화란**

- **입력:** 픽셀 배열·파일 형태의 **비정형 이미지** (구조·스키마 없음).
- **출력:** **정형에 가까운 표현** — 예) 고정 차원의 **텐서(수치 배열)**, **테이블/JSON** 형태의 추출 결과(OCR·객체·캡션 등).
- **파이프라인 요약:** 입력 정규화 → **비전/멀티모달 모델**로 분석 → **스키마에 맞는 구조화(JSON·테이블·임베딩)** → 검증·저장. (Roboflow, Azure 멀티모달 처리 등에서 이미지→구조화 JSON 추출 워크플로 제시.)

**2. 멀티모달과 이미지 내부 구조·함의**

- **멀티모달 학습:** 서로 다른 데이터 유형(이미지, 텍스트, 음성, 3D 등)을 **공통 잠재공간(latent space)** 에 투영해, 의미적으로 비슷한 내용이 가까운 벡터로 매핑되도록 한다. 이미지 “내부”의 **구조(객체·레이아웃·채널)** 와 **함의(의미·캡션·태그)** 를 뽑아 텍스트·다른 모달과 정렬할 수 있다.
- **구조:** CNN/ViT 등으로 **공간적 구조**(높이×너비×채널), **계층적 특징**(저수준 엣지 → 고수준 의미)이 학습된다.
- **함의:** Vision-Language Model(VLM), Pix2Struct 등은 이미지를 **문서/HTML/JSON** 같은 **구조화된 형식**으로 파싱하거나, **캡션·QA·요약** 등 의미 정보로 변환한다.

**3. 컬러 이미지의 3D 텐서 표현 — 플로우·방법·전제·로직**

- **3차원 텐서:** 컬러 이미지는 **높이(H) × 너비(W) × 채널(C)** 의 **3D 텐서**로 표현된다. RGB면 **C=3** (Red, Green, Blue). 픽셀 강도는 보통 0~255 → 정규화 시 0~1.
- **레이아웃 관례:** PyTorch는 **[C, H, W]** (채널 우선), 다른 프레임워크는 **[H, W, C]**. 배치면 **[N, C, H, W]** (N=이미지 개수). 이 **고정된 shape**이 일종의 “스키마”처럼 동작해, 이후 레이어·연산이 일관되게 적용된다.
- **플로우(이미지→이미지):**  
  **입력 이미지** → **인코더** → **잠재 표현(latent)** 또는 **토큰 시퀀스** → **디코더/플로우** → **재구성 이미지** 또는 **다른 이미지**.  
  예: **FlowMo** 같은 방식은 트랜스포머 기반 디퓨전 오토인코더로, 인코더가 이미지를 연속 잠재공간으로, 디코더가 플로우(속도장)를 통해 노이즈 이미지를 복원한다. “이미지→이미지”는 **같은 모달 내 변환**(스타일, 해상도, 인페인팅) 또는 **잠재공간 편집**으로 이어질 수 있다.
- **전제:** (1) 이미지를 **고정 크기·채널**로 정규화할 수 있다. (2) **잠재공간** 또는 **토큰**이 이미지의 구조·함의를 담기에 충분하다. (3) **비정형 픽셀**이 **정형에 가까운 수치 텐서**로 변환되면, 수학적 연산·모델·저장이 일관된다.
- **로직:** 픽셀 → 컨볼루션/패치 임베딩 → 특징 맵/시퀀스 → 인코더 레이어 → 잠재 벡터/토큰 → (선택) 플로우/디퓨전/디코더 → 재구성 또는 다른 모달(텍스트·JSON)로 매핑.

**4. 관련 키워드와 상호관계**

| 키워드 | 의미 | 상호관계 |
|--------|------|-----------|
| **정형화** | 비정형 데이터를 고정 구조·스키마·타입에 맞게 변환 | 목표; 이미지→텐서/테이블/JSON이 예시 |
| **3D 텐서 (H×W×C)** | 이미지의 수치적 표현; RGB면 C=3 | 정형화된 “이미지 한 장”의 기본 단위 |
| **멀티모달** | 이미지·텍스트·음성 등 다중 모달을 공통 공간에 매핑 | 정형화 결과를 다른 모달과 정렬·융합 |
| **잠재공간 (latent space)** | 인코더가 만드는 저차원 연속 표현 | 이미지→이미지 플로우의 중간 단계 |
| **인코더–디코더** | 입력→잠재→재구성/출력 파이프라인 | 플로우·디퓨전·재생성의 골격 |
| **VLM / Pix2Struct** | 이미지를 텍스트·구조(HTML/JSON)로 파싱 | 비정형 이미지→정형(스키마 기반) 출력 |
| **Flow / 디퓨전** | 잠재공간 또는 픽셀 공간에서의 변환 과정 | 이미지→이미지 변환·편집의 방법론 |
| **스키마** | 출력 구조·필드·타입의 사전 정의 | 정형화된 추출 결과(JSON·테이블)의 형식 |

**5. 요약**

- **비정형 이미지**는 **정형 데이터(행·열·스키마)** 와 대비될 때, **정형화**의 전형적 입력이다.
- **멀티모달**은 이미지 내부 **구조·함의**를 뽑아 텍스트·구조화 출력과 연결하고, **컬러 이미지**는 **3D 텐서(RGB, [C,H,W])** 로 표현되어 **플로우(인코더→잠재→디코더)** 와 **이미지→이미지/이미지→정형** 파이프라인의 기반이 된다.
- **전제·로직**은 “픽셀을 고정 shape 텐서로 정규화 → 잠재공간 또는 토큰으로 압축 → 연산·재구성·스키마 기반 출력”으로 요약할 수 있다.

#### 자료구조·파일 형식 관점: 파이썬 딕셔너리, JSON, CSV, TSV, RSS

**자료구조란?**

- **정의:** **주어지는 데이터를 어떻게 저장하고 관리할지**를 정한 구조이다. “무엇을(데이터)”이 아니라 “**어떤 방식으로** 담고, 꺼내고, 찾고, 바꿀 것인가”를 결정하는 것이다.
- **예:** 호랑이, 소, 돼지, … 처럼 항목을 **순서대로만** 넣어 두는 것도 한 방식이고, “이름으로 바로 찾기”, “가장 큰 값만 빠르게 꺼내기”처럼 **목적에 맞게** 저장·접근 방식을 바꾼 것도 자료구조이다.

**가장 단순한 방식: 리스트(배열)**

- **리스트:** 데이터를 **순서대로** 나열해 두는 구조. **인덱스(0, 1, 2, …)** 로 “몇 번째인가”가 정해지므로 **가장 직접적**이고, “i번째 항목 보기”는 한 번에 가능하다.
- **장점:** 구현이 단순하고, “순서대로 돌면서 다 보기”가 쉽다.
- **한계:** **쿼리·분석·정렬**에서 막힌다.  
  - “주어진 데이터 값 중 **가장 큰 값**은?” → **매번 전체를 다 봐야** 한다(천 개면 천 번 확인).  
  - “특정 조건을 만족하는 것만 골라라”, “정렬된 순서로 유지하면서 넣어라” 같은 요구도 **리스트만으로는 비효율**이다.  
  즉, **저장은 쉽지만 “찾기·정렬·집계”** 를 할 때마다 **전부 스캔**해야 하는 구조다.

**그래서 나온 것: 노드·링크 방식**

- **아이디어:** “천 개 데이터를 **그냥 리스트 한 줄**로만 저장하지 말고, **노드(node)** 와 **링크(link)** 로 묶어서, **연산 목적에 맞는 형태**로 저장하자.”
- **노드:** 데이터 한 덩어리(값 + 필요한 메타정보)를 담는 단위.  
- **링크:** 노드와 노드 사이의 **관계(포인터/참조)**. “다음 누가 있는가”, “부모/자식은 누구인가” 등을 링크로 표현한다.
- **효과:**  
  - **연결 리스트:** “다음”만 링크하면, 중간 삽입·삭제는 링크만 바꾸면 되어 리스트 전체를 밀 필요가 없다.  
  - **트리(이진 탐색 트리 등):** “왼쪽은 작은 값, 오른쪽은 큰 값”처럼 링크를 정해 두면, **최댓값·최솟값·특정 값 찾기**를 **전체를 다 보지 않고** 절반씩 줄여 가며 할 수 있다.  
  - **힙:** “부모가 자식보다 크다(또는 작다)” 같은 링크 구조로 “**가장 큰 값(또는 작은 값)**”을 **한 번에** 꺼내는 연산을 지원한다.  
  즉, **저장 구조를 “노드+링크”로 바꾸면**, “가장 큰 값”, “정렬”, “조건 검색” 같은 **쿼리·분석**을 **전부 보지 않고** 더 빠르게 할 수 있다.

**정리**

| 방식 | 저장 | 쿼리(최댓값·정렬·검색 등) |
|------|------|-----------------------------|
| **리스트(순서·인덱스)** | 단순, 직접, 인덱싱 쉬움 | 매번 전체 스캔 → 데이터 많으면 비효율 |
| **노드·링크(연결 리스트, 트리, 힙 등)** | 노드+링크로 관계를 명시 | 구조에 따라 부분만 탐색 → 효율적 쿼리·정렬 가능 |

- 데이터가 많아질수록 “**어떤 자료구조로 저장·관리할지**”가 **조회·정렬·분석 속도**를 좌우한다. 그래서 **리스트**는 “가장 단순·직접”이지만, **노드·링크 기반 구조**가 쿼리·소팅 등에서 선택되는 이유이다.

데이터의 **구조**를 “메모리/코드 안의 자료구조”와 “파일·스트림의 문법”으로 나누어 보면, **파이썬 딕셔너리**와 **JSON·CSV·TSV·RSS** 등이 서로 대응·변환 관계를 이룬다. (웹 자료 기준으로 정리.)

**1. 파이썬 딕셔너리 (자료구조 측면)**

- **정의:** **키(key)–값(value)** 쌍의 집합. 순서(3.7+ 보장), **O(1) 조회**, 중첩 가능(딕셔너리·리스트 안에 딕셔너리).
- **JSON과의 대응:** JSON의 **객체(object)** 는 중괄호 `{}` 로 감싼 키–값 쌍이며, **파이썬 dict와 1:1 대응**한다. 문자열은 JSON에서는 쌍따옴표만, 불리언은 `true`/`false`(소문자). 리스트/튜플은 JSON 배열 `[]` 로 직렬화.
- **직렬화/역직렬화:** `json.dumps(dict)` → JSON 문자열, `json.dumps(dict, indent=2)` → 보기 좋은 출력. `json.loads(str)` → dict. `json.dump()`/`json.load()` 는 파일 입출력용. (Python 표준 라이브러리 `json` 모듈.)

**2. JSON (JavaScript Object Notation)**

- **문법:** 객체 `{}`, 배열 `[]`, 키–값(문자열·숫자·불리언·null·중첩 객체·배열). **계층 구조**로 중첩 가능.
- **특징:** 웹 API·설정 파일·반정형 저장에 널리 쓰임. **스키마 검증**(JSON Schema) 가능. CSV/TSV보다 용량·파싱 비용이 크지만 **계층·다중 속성** 표현에 유리.

**3. CSV (Comma-Separated Values)**

- **문법:** **쉼표(`,`)** 로 필드 구분, 한 줄에 **한 레코드(행)**. 첫 줄을 헤더(컬럼명)로 쓰는 경우 많음. 필드 안에 쉼표·줄바꿈이 있으면 따옴표로 감싸고 이스케이프.
- **특징:** **평면·테이블형**. 엑셀·스프레드시트 호환 좋음. 데이터에 쉼표·따옴표가 많으면 이스케이핑이 필요해 파싱이 까다로울 수 있음.

**4. TSV (Tab-Separated Values)**

- **문법:** **탭(`\t`)** 으로 필드 구분, 한 줄에 한 레코드. CSV와 동일한 “행=레코드, 열=필드” 구조.
- **특징:** **쉼표가 데이터에 자주 나오는 경우**(금액, 주소 등) CSV보다 유리. 로그·연구용 테이블·내부 파이프라인에서 자주 사용. (NCBI 등에서 CSV/TSV·JSON 비교 문서 제시.)

**5. RSS (Really Simple Syndication)**

- **문법:** **XML 1.0** 기반. 루트 `<rss version="2.0">` 안에 `<channel>`(제목·링크·설명·언어 등 메타), `<item>`(개별 항목: 제목·링크·설명·날짜·작성자·카테고리 등). 태그로 구조가 정해져 있음.
- **특징:** **웹 콘텐츠 배포·구독**용. 블로그·뉴스 피드. 반정형(XML)이며, 파싱 시 태그 이름으로 필드 추출. JSON·CSV처럼 “단순 키–값”이 아니라 **XML 트리** 구조.

**6. 형식 간 관계 요약**

| 구분 | 자료구조/문법 | 구조 | 용도·특징 |
|------|----------------|------|-----------|
| **파이썬 dict** | 키–값, 중첩 가능 | 계층 | 메모리 내 표현, JSON과 직렬화 호환 |
| **JSON** | `{}` `[]`, 키–값 | 계층 | API·설정·반정형 저장, dict↔문자열 변환 |
| **CSV** | `,` 구분, 행단위 | 평면(2차원) | 스프레드시트, 단순 테이블, 호환성 |
| **TSV** | `\t` 구분, 행단위 | 평면(2차원) | 쉼표 많은 데이터, 로그·연구용 |
| **RSS** | XML 태그 (`<channel>`, `<item>`) | 트리(XML) | 피드·배포, 구독용 |

- **데이터 타입과의 연결:** 정형(테이블)에 가까운 것 → CSV, TSV. 반정형(계층·태그) → JSON, RSS(XML). 파이썬에서는 **dict → JSON** 변환이 정형화·API 입출력의 기본 단위가 된다.

수리·통계 관점에서 변수(데이터)를 **연속형**과 **이산형**으로 나누어 이해한다.

### 1) 수리·통계 측면 — 연속형 / 이산형

#### 연속형 (Continuous)

- **결과가 무한히 많은 변수 데이터.** 일정 범위 안에서 **어떤 값이든** 가질 수 있다.
- **측정 도구의 정밀도**에 따라 소수점 아래로 **무한히 쪼갤 수 있다.** (예: 길이, 무게, 온도, 시간)
- 구간 상의 두 값 사이에 항상 다른 값을 생각할 수 있으므로, **연속적인 스케일**로 취급한다.

#### 이산형 (Discrete)

- **측정 결과를 셀 수 있는 데이터.** **정수 형태**가 많다.
- **개수, 횟수** 등으로 표현되는 변수. (예: 사건 횟수, 인원 수, 결함 개수)
- 값과 값 사이에 “반쯤” 같은 것이 정의되지 않으며, **딱딱 끊어진 값**만 가진다.

| 구분 | 연속형 | 이산형 |
|------|--------|--------|
| **값의 개수** | (이론상) 무한 | 셀 수 있음(유한 또는 가산) |
| **형태** | 소수점 가능, 구간 상 연속 | 정수·횟수·개수 등 |
| **예** | 길이, 무게, 온도, 시간 | 인원 수, 사건 횟수, 결함 개수 |

### 데이터의 분류 2) 자료분석 측면

**자료분석(척도)** 관점에서는 **수치형(측정형)** 과 **범주형**으로 나누고, 수치형을 다시 **등간척도**와 **비율척도**로, 범주형을 **명목척도**와 **서열(순서)척도**로 구분한다.

#### 수치형 (측정형) — Numeric / Measurable / Quantitative

- **등간척도 (Interval scale):** 순서뿐만 아니라 **속성 간 간격이 일정한** 척도. **절대적 영점이 없어** “두 배” 같은 **비율 계산은 어렵다.** 예: 온도(℃), 지능지수(IQ), 날짜 등.
- **비율척도 (Ratio scale):** 등간척도의 특징에 더해 **절대적 영점이 존재**한다. **0은 “아무것도 없음”**을 의미해 **모든 산술연산**(비율, 배수)이 가능하다. 예: 키, 몸무게, 나이, 소득, 가격, 학생 수 등.

#### 범주형 — Non-metric

- **명목척도 (Nominal scale):** 단순히 **이름이나 카테고리**만 구분. **산술연산 불가.** 예: 성별, 혈액형, 거주지역(서울/부산 등), 선호 등.
- **서열(순서)척도 (Ordinal scale):** 카테고리 간에 **순서나 등급**이 있는 척도. 수치가 있어도 **간격이 일정하지 않다.** 예: 학력, 직급, 만족도, 서열·등급 등.

| 구분 | 수치형(측정형) | 범주형 |
|------|----------------|--------|
| **척도** | 등간척도, 비율척도 | 명목척도, 서열척도 |
| **특징** | 간격·비율 해석 가능(비율척도는 영점 있음) | 이름·순서만, 산술연산 제한 |
| **예** | 온도, IQ, 키, 가격, 학생 수 | 성별, 혈액형, 거주지역, 학력, 직급, 만족도 |

### 데이터의 분류 3) 시계열 관점

- **시계열 데이터:** **시간 순서**대로 관측된 데이터. 시점·구간별로 기록되며 **추세, 계절성, 주기** 등 시간에 따른 패턴이 분석 대상이 된다.
- **관점:** 같은 변수라도 “언제” 측정되었는지가 중요하고, **과거→현재** 순서를 바꿀 수 없으며, 예측·포캐스팅 시 **시점 정보**를 반드시 활용한다. 예: 일별 매출, 센서 로그, 주가, 기상 데이터 등.

### 데이터의 분류 4) 인과/상관관계 관점

- **데이터분석의 목적**은 결국 **“X가 변할 때 Y가 어떻게 변하는가”**를 이해하는 것이다. 변수 역할을 나누어 보는 관점이다.
- **설명변수 (독립변수, X):** 원인·입력·조건으로 보는 변수. “이것을 바꾸면?”의 주체.
- **반응변수 (종속변수, Y):** 결과·출력·설명 대상. “이것이 어떻게 달라지는가?”의 대상.
- **머신러닝과의 연결:** 머신러닝도 **입력(X) → 출력(Y)** 관계를 학습·예측하는 것이 핵심이다. 회귀·분류 모두 “X가 주어졌을 때 Y를 맞추거나 설명하는” 문제로 정리된다.

| 용어 | 동의어 | 역할 |
|------|--------|------|
| **설명변수** | 독립변수, X, 입력(피처) | 변할 때 결과에 영향을 주는 쪽 |
| **반응변수** | 종속변수, Y, 출력(타깃) | 설명·예측의 대상 |

### 데이터의 분류 5) Data vs Information vs Knowledge vs Wisdom (DIKW)

**데이터(Data)·정보(Information)·지식(Knowledge)·지혜(Wisdom)** 를 구분하는 **DIKW 계층**은 데이터사이언스·정보관리·지식관리의 핵심 개념이다. **Russell L. Ackoff(1989)** 가 “From Data to Wisdom”에서 체계적으로 정리한 이후, **DIKW hierarchy / Knowledge pyramid** 로 널리 인용된다. (웹 자료·원문 인용 반영.)

**1. 정의 (실무·강의용 요약)**

| 단계 | 한글 | 정의 요약 | 키워드 |
|------|------|-----------|--------|
| **Data** | 데이터 | 관찰의 결과로 나타난 **정량·정성의 실제 값**. 원시 사실(raw facts), 아직 해석되지 않은 기호·측정값. | raw facts, 관찰, 기호(symbols) |
| **Information** | 정보 | 데이터에 **맥락(context)** 과 **해석(interpretation)** 을 부여한 것. “누가, 무엇을, 언제, 얼마나”에 대한 **설명(description)** 이며, **데이터로부터 추론(inferred from data)** 된다. | context + interpretation, who/what/when/how many |
| **Knowledge** | 지식 | **노하우(know-how)**. “어떻게 작동하는가”, “어떻게 할 것인가”에 대한 이해. **정보를 명령·행동 지침(instructions)** 으로 변환하는 단계. **행동 가능한 통찰(actionable insight)**. | know-how, how, information → instructions |
| **Wisdom** | 지혜 | **가치(value)** 를 더하고 **판단(judgement)** 을 요구한다. 효율(efficiency)을 넘어 **효과(effectiveness = efficiency × value)** 와 **미래에 대한 선택**을 다룬다. 비결정적·윤리·가치 판단. | judgement, value, effectiveness |

**2. Ackoff(1989) 원문 요지**

- **Data:** “Data are **symbols** that represent properties of **objects, events and their environment**. They are the **products of observation**.” — 객체·사건·환경의 속성을 나타내는 **기호**이며, **관찰의 결과물**.
- **Information:** “Information is contained in **descriptions**, answers to questions that begin with **who, what, when, how many**. Information is **inferred from data**.” — **설명**과 질문에 대한 답에 담기며, **데이터로부터 추론**된다.
- **Knowledge:** “Knowledge is **know-how**; e.g. **how a system works**. It is what makes possible the **transformation of information into instructions**.” — **노하우**이며, **정보를 명령(지침)** 으로 바꾸는 단계.
- **Wisdom:** “Wisdom **adds value**, which requires the mental function we call **judgement**.” — **가치**를 더하며, **판단**이라는 정신 기능이 필요하다.

> **출처:** Ackoff, R. L. (1989). From data to wisdom. *Journal of Applied Systems Analysis*, 16(1), 3–9.

**3. DIKW 계층의 성격 (웹 그라운딩 반영)**

- **계층 구조:** Data → Information → Knowledge → Wisdom 순으로 **아래 단계가 위 단계의 기반**이 된다. “No wisdom without knowledge, no knowledge without information, no information without data.”
- **양의 비대칭:** 상위로 갈수록 **양이 줄어든다**는 해석이 있다(예: 데이터는 많고, 지혜는 희소). 데이터사이언스는 **데이터·정보**를 늘리고, **지식·(가능하면) 지혜**로 전환하는 것이 목표다.
- **지혜의 특수성:** 지혜는 **미래를 창조하는 선택**과 **가치·윤리·판단**을 포함하며, **컴퓨터 시스템만으로는 생성하기 어렵다**는 견해가 있다(Ackoff 등). 데이터·정보·지식은 자동화·ML로 보강 가능하나, “무엇이 옳은가”는 인간의 판단 영역으로 남는 경우가 많다.

**4. 예시: 체온**

| 단계 | 내용 |
|------|------|
| **Data** | 아침에 측정한 4살 민수의 체온 **38.2°C** (측정된 숫자만). |
| **Information** | 정상 범위(36.5~37.5°C) 기준 **높음** → **발열 상태** (숫자에 임상적 의미 부여). |
| **Knowledge** | 발열은 **감염(독감·코로나 등)** 의 대표적 초기 증상 → **휴식 또는 병원 진료**가 필요하다는 노하우. |
| **Wisdom** | 이 아이에게 지금 “병원을 가는 것”이 **가치 있는지**, 다른 제약(시간·비용·위험)을 고려한 **판단**. |

**5. 예시: 매출(장바구니)**

| 단계 | 내용 |
|------|------|
| **Data** | 대형마트에서 **동일 영수증 내 기저귀·맥주 동시 등장 비율 26%**, **19:00~21:00** 시간대. |
| **Information** | 기저귀 구매 고객이 **맥주를 함께 구매**한다. 두 상품 간 **매출 연관성**이 존재한다(맥락·해석). |
| **Knowledge** | **기저귀 진열 위치 옆에 시원한 맥주 냉장 코너를 배치**하면 매출을 극대화할 수 있다는 **실행 가능한 지침**. |
| **Wisdom** | “그렇게 배치하는 것이 이 마트·이 지역·이 시기에 **정말 옳은가**”에 대한 **가치·판단**(예: 음주·육아 메시지 정합성, 브랜드 이미지 등). |

**6. 데이터사이언스와의 연결**

- **데이터** 수집·저장·정제 → **정보** 도출(시각화, 요약, “누가·무엇·언제·얼마나”에 대한 답) → **지식** 생성(모델·규칙·노하우, “어떻게” 행동할지) → (가능한 범위에서) **지혜** 지원(의사결정·가치 판단을 위한 입력 제공).  
- 분석·ML은 주로 **Data → Information → Knowledge** 구간을 강화하고, **Wisdom** 은 인간의 판단·윤리·목표 설정과 결합할 때 완성된다.

## 4. 데이터사이언스의 암(暗)에 대하여

데이터사이언스가 가지는 **어두운 면·난제**를 인지할 필요가 있다.

- **용어의 모호성과 광범위한 스펙트럼:** “데이터사이언스”라는 말 하나로 **단순 통계·설문 분석**부터 **AI·딥러닝·대규모 모델링**까지 아우르기 때문에, 사람마다·상황마다 의미가 다르게 쓰인다.
- **정의의 모호함:** 학계·산업계·직무별로 정의가 제각각이다. “데이터 분석가”, “데이터 사이언티스트”, “ML 엔지니어” 등 역할 경계도 흐릿하다.
- **학습 선호와 커버리지:** **통계 이론**을 중시하는 쪽과 **코드·엔지니어링**을 중시하는 쪽이 공존하는데, 한 강의·한 과정에서 **통계와 코드를 동시에 골고루** 다루기 어렵다. 학습자 선호(통계 vs 코딩)에 따라 “부족하다”고 느끼는 부분이 달라진다.

> 이 암(暗)을 인지하고, 자신의 목표(연구·실무·비즈니스)에 맞게 **어디에 깊이를 둘지** 선택하는 것이 중요하다.

---

## 5. 데이터사이언스에 대한 불편한 진실

데이터사이언스 업무·역할이 겪는 **불편한 현실**을 직시할 필요가 있다.

- **누구도 너가 무엇을 했는지 알 바가 없다.** 분석·전처리·모델링·해석은 대부분 “블랙박스”처럼 인식된다. 경영진·동료는 **결과(지표 개선, 인사이트)** 만 보지, 그 뒤의 데이터 정제·가설·한계를 구분하지 못하는 경우가 많다. 그래서 **무엇을 했는지 스스로 기록·공유·스토리텔링**하는 역량이 중요해진다.
- **아카데미아와 비즈니스(실무)의 기대가 다르다.** 아카데미아는 **재현성·이론·논문·검증**을 중시하고, 비즈니스는 **속도·결과·ROI·배포**를 중시한다. 같은 “모델”이라도 학계에서는 가정·통계적 유의성이, 실무에서는 “얼마나 빨리 개선되는가”가 평가 기준이 된다. 두 세계를 오가며 일할 때 이 갈등을 인지하고, **누구를 위한 결과물인지**를 명확히 하는 것이 중요하다.

---

## 6. 다학제적 융합과 전문지식

- **데이터 자체의 지식만큼, 해당 산업군의 도메인 전문성이 필수적이다.** 데이터만 잘 다루고 비즈니스·산업 맥락을 모르면 해석과 행동 제안이 빗나간다.
- **다양한 분야의 전문가들과 소통·협업하는 역량**이 성패를 좌우한다. — 기획·마케팅·엔지니어링·법무·윤리 등과 함께 일할 때, “데이터로 무엇을 묻고, 어떤 결정을 바꿀 것인가”를 같이 설계할 수 있어야 한다.

| 축 | 요약 |
|----|------|
| **데이터 역량** | 수집·정제·분석·모델링·시각화 |
| **도메인 전문성** | 산업·비즈니스·문제 맥락 이해 |
| **협업·소통** | 비데이터 전문가와 목표·제약·해석 공유 |

## 7. 데이터 윤리와 보안체계

- **보안 및 프라이버시:** 개인정보·민감 데이터의 수집·저장·이용 시 **보안 체계**(접근 통제, 암호화, 감사 로그)와 **프라이버시 보호**(최소 수집, 목적 제한, 동의)가 필수이다.
- **윤리적 책임:** 데이터로 만든 모델·자동화가 **차별**, **편향**, **감시**로 이어지지 않도록 설계·검토·거버넌스가 필요하다. “할 수 있는 것”과 “해도 되는 것”을 구분하는 **데이터 윤리** 의식이 중요하다.

---

## 8. 데이터에 대한 분명한 진실

실무에서 자주 맞닥뜨리는 **데이터의 현실**을 직시할 필요가 있다.

- **데이터는 절대 클린하지 않다.** 이상치, 결측, 스케일 불일치, 레이블 오류, 수집 편향 등이 항상 존재한다. “깨끗한 데이터”를 전제로 한 이론과 달리, 현장 데이터는 거의 항상 정제가 필요하다.
- **너는 대부분의 시간을 전처리하는 데 보낸다.** 설문·경험에 따르면 데이터 과학자 시간의 상당 부분(40~80% 등)이 수집·정제·가공·EDA에 쓰인다. 모델링보다 **데이터 이해와 전처리**가 실제 업무의 중심이다.
- **95% 이상은 딥러닝에 불필요하다.** 대부분의 비즈니스·분석 문제는 **딥러닝 없이** 해결 가능하다. 상대적으로 단순한 모델·규칙·통계로 충분한 경우가 많고, 딥러닝은 데이터·리소스·해석성이 요구되는 특정 문제에 한해 선택하는 것이 합리적이다.
- **90% 이상의 제너럴라이즈드 리니어 리그레션(GLM) 활용은 트릭(함정)을 발생시킨다.** 선형·로지스틱 회귀 등 GLM을 잘못 가정하거나 전제를 무시해 쓰면 **오해·과대해석·잘못된 인과 추론** 등 함정에 빠지기 쉽다. 분포 가정, 연결함수, 이분산성, 다중공선성 등을 제대로 다루지 않으면 “트릭”이 된다.
- **랜덤 포레스트(Random Forest)와 XGBoost는 여전히 언제나 파워풀하다.** 구조가 단순하고 튜닝 부담이 상대적으로 적으면서도, 테이블형 데이터에서 **예측력·안정성**이 뛰어나다. 딥러닝이 답이 아닐 때, **기본 무기**로 두는 것이 현실적인 선택이다.

| 메시지 | 요약 |
|--------|------|
| 데이터는 클린하지 않다 | 전처리·검증이 필수 |
| 시간은 전처리에 | 모델링보다 데이터 이해·정제 비중이 큼 |
| 딥러닝은 5% 미만 | 대부분의 문제는 더 단순한 방법으로 충분 |
| GLM 함정 | 가정·전제 무시 시 오해·트릭 발생 |
| RF·XGBoost | 테이블 데이터에서 여전히 강력한 기본기 |

## 9. 페더레이티드 러닝과 엣지 컴퓨팅

프라이버시·지연·대역폭 제약이 있는 환경에서 데이터를 다루는 방식과 관련된 두 가지 중요한 트렌드를 웹 자료 기준으로 정리한다.

### 9.1 페더레이티드 러닝 (Federated Learning, FL)

- **정의:** 여러 클라이언트(모바일 기기, 엣지 노드, 기관 서버 등)가 **민감한 원본 데이터를 한곳으로 모으지 않고**, 각자 로컬에서 학습한 **모델 업데이트(가중치·그래디언트)** 만 서버로 보내서 합치고, **공통 글로벌 모델**을 함께 학습시키는 **분산 머신러닝** 방식이다.
- **동작:** 로컬에서 학습 → 업데이트만 전송 → 서버에서 **Federated Averaging (FedAvg)** 등으로 집계 → 갱신된 글로벌 모델을 다시 클라이언트에 배포하는 사이클을 반복한다.
- **프라이버시:** 원본 데이터가 기기/기관 밖으로 나가지 않으므로, 의료·금융·IoT 등 **GDPR·HIPAA** 등 규제가 엄한 분야에서 활용된다. **차등 프라이버시(Differential Privacy)** 로 업데이트에 노이즈를 더하거나, **Secure Aggregation(SecAgg)** 으로 서버가 개별 업데이트를 보지 못하게 할 수 있다.
- **한계:** 디바이스 간 데이터 분포가 다름(Non-IID), 하드웨어·통신 이질성, 통신 비용·라운드 수 등이 이슈가 된다.
- **사례:** 구글의 스마트 텍스트 추천(Android), 의료·금융 협업 학습 등.

### 9.2 엣지 컴퓨팅 (Edge Computing)

- **정의:** 연산과 저장을 **데이터가 생성되는 곳(네트워크 말단, 엣지)** 에 가깝게 두어, 중앙 데이터센터로 보내기 전에 **현장에서 처리**하는 분산 컴퓨팅 모델이다. 지연을 줄이고 대역폭·프라이버시 부담을 낮춘다.
- **데이터·IoT와의 관계:** IoT·센서·공장·매장 등에서 발생하는 데이터가 폭증하면서, 전부 클라우드로 보내면 **지연·비용·보안** 문제가 커진다. 엣지에서는 **원시 데이터를 현장에서 전처리·집계·추론**하고, 필요한 결과만 중앙으로 보내는 구조가 일반적이다.
- **장점:** **저지연**(실시간 반응), **대역폭 절감**, **네트워크 끊겨도 동작 가능**(오프라인 구간 처리), **민감 데이터를 로컬에 유지**할 수 있어 프라이버시·규제 대응에 유리하다.
- **데이터사이언스 관점:** 수집·전처리·모델 배포가 “클라우드 중심”에서 “엣지·클라우드 혼합”으로 바뀌고 있으며, **엣지에서의 실시간 추론·페더레이티드 러닝**과 결합되는 사례가 늘고 있다.

| 구분 | 페더레이티드 러닝 | 엣지 컴퓨팅 |
|------|-------------------|-------------|
| **초점** | 데이터를 모으지 않고 분산 학습 | 연산·저장을 데이터 발생지 인근으로 이동 |
| **목적** | 프라이버시 보존 + 협업 학습 | 지연 감소, 대역폭·비용 절감, 실시간성 |
| **데이터** | 원본은 로컬, 업데이트만 교환 | 원시 데이터를 엣지에서 처리·집계 후 전송 |

## 10. 데이터 관리 측면: 데이터베이스와 데이터 품질

데이터사이언스는 “데이터를 어떻게 **저장·관리·품질 관리**할 것인가”가 전제된다. **데이터베이스**의 개념과 **데이터 품질**의 체계를 정리한다. (강의교안·웹 자료 반영.)

### 10.1 데이터 관리 측면에서의 데이터 ~ 데이터베이스

#### 데이터베이스의 개념

**데이터베이스**는 **여러 사람이 공용으로 사용하기 위해 통합하고 저장한 운영 데이터의 집합**이다. (DBMS를 통해 조직·저장·관리되는 데이터의 집합이라는 정의와도 맞닿아 있다.)

| 특성 | 설명 |
|------|------|
| **공용 데이터 (Shared data)** | 한 사람 또는 한 업무만을 위한 데이터가 아니라 **공동으로 사용**되는 데이터. 다수의 사용자·업무가 동시에 접근·활용할 수 있도록 설계된다. |
| **통합된 데이터 (Integrated data)** | 각 부서·시스템에서 따로 쓰던 데이터를 **하나로 통합**하는 개념. **중복을 최소화**하여 **중복으로 인한 데이터 불일치**를 제거한다. 동일한 고객·제품 정보가 여러 곳에 서로 다르게 있으면 신뢰도가 떨어지므로, 단일 소스로 통합·관리한다. |
| **저장된 데이터 (Stored data)** | 문서·종이로 보관하는 것이 아니라 **디스크, 테이프** 등 **컴퓨터 저장장치**에 저장된 데이터. 검색·갱신·백업·복구가 체계적으로 이루어진다. |
| **운영 데이터 (Operational data)** | **조직의 목적**을 위해 사용되는 데이터. 즉 **업무 수행**(검색·등록·수정·삭제)을 **목적으로 저장**된 데이터. 일상적 트랜잭션·업무 시스템에서 생성·활용되는 데이터를 말한다. |

- **DBMS(Data Base Management System):** 데이터베이스를 생성·조회·갱신·삭제하고, 보안·동시성·무결성을 관리하는 소프트웨어. 관계형 DB(SQL), NoSQL 등 다양한 모델이 있다.

---

### 10.2 데이터 품질 (Data Quality)

#### 데이터 품질이란

- **정의:** 데이터의 **최신성, 정확성, 상호연계성** 등을 확보하여, **사용자에게 유용한 가치**를 줄 수 있는 수준을 말한다. 품질이 낮은 데이터는 분석·의사결정·모델의 결과를 왜곡한다.
- **데이터 품질 = 구조적 품질(Syntactic) + 내용적 품질(Semantic)**  
  — “형식이 맞는가”와 “의미·현실을 제대로 반영하는가”를 함께 봐야 한다.

#### 구조적 품질 (Syntactic Quality)

데이터가 **규정된 형식(Format), 제약 조건(Constraint), 스키마(Schema)** 를 얼마나 잘 준수하는가를 의미한다.

| 차원 | 설명 | 예시 질문 |
|------|------|------------|
| **완전성 (Completeness)** | 필수 항목에 **누락(Null)** 이 없는가? | 주문 테이블에서 “고객 ID”가 비어 있지 않은가? |
| **유효성 (Validity)** | **데이터 타입**과 **허용 범위**를 만족하는가? | 숫자 칸에 문자가 들어가 있지 않은가? 코드가 허용 목록에 있는가? |
| **일관성 (Consistency)** | 데이터 **형식**이 전반적으로 **통일**되어 있는가? | 날짜가 모두 YYYY-MM-DD로 통일되어 있는가? 동일 개념이 서로 다른 표기로 섞여 있지 않은가? |

#### 내용적 품질 (Semantic Quality)

데이터가 **현실 세계의 실제 값(Ground Truth)** 을 얼마나 정확하게 반영하고 있는가를 의미한다.

| 차원 | 설명 | 예시 질문 |
|------|------|------------|
| **정확성 (Accuracy)** | 기록된 값이 **실제 사실**과 일치하는가? | 고객 주소가 실제 거주지와 같은가? |
| **정밀성 (Precision)** | 데이터가 **충분히 상세하게** 기록되었는가? | “서울시”만 있는가, “동·상세주소”까지 있는가? |
| **최신성 (Currency / Timeliness)** | 데이터가 **현재 시점**을 반영하고 있는가? 필요할 때 **제때** 사용 가능한가? | 휴대폰 번호가 최근 변경분을 반영하는가? |

- **참고:** IBM·Conduktor 등에서도 정확성(Accuracy), 완전성(Completeness), 일관성(Consistency), 유효성(Validity), 적시성(Timeliness), 유일성(Uniqueness) 등을 데이터 품질 차원으로 제시한다. 구조적(형식·스키마 준수)과 내용적(현실 반영·의미) 구분은 품질 관리 실무에서 함께 쓰인다.

#### 데이터 품질 관리의 체계화

- **정보 생명주기:** 데이터의 **구축 → 운영 → 활용**까지 **정보 생명주기(Information Lifecycle)** 를 고려하여, **전 단계**에 걸쳐 품질이 적용되도록 **체계**를 갖출 필요가 있다. 수집·저장 시점의 검증, 운영 중 정기 점검, 활용 전 품질 평가가 연결되어야 한다.
- **공공데이터포털:** 데이터 품질·공개·활용의 대표 사례. [공공데이터포털 (data.go.kr)](https://www.data.go.kr) 에서 공공기관이 제공하는 데이터셋을 검색·다운로드할 수 있으며, 메타데이터·형식·이용 조건이 정리되어 있다. 공공 데이터의 **품질·표준화·개방**을 한곳에서 접근할 수 있다.

## 11. 빅데이터

빅데이터는 **단순히 “많은 데이터”가 아니라**, **3V(규모·속도·다양성)** 라는 기술적 한계를 극복하고, **비정형 데이터**에서 새로운 통찰을 추출하여 **인공지능 및 데이터 기반 경제**의 핵심 원동력이 되는 **디지털 자산**으로 이해된다. (강의 요지·웹 그라운딩 반영.)

### 11.1 빅데이터의 정의

- **핵심 정의:**  
  단순한 “많은 데이터”를 넘어, **3V(Volume, Velocity, Variety)** 라는 **기술적 한계**를 극복하고, **비정형 데이터**에서 **새로운 통찰**을 추출하여 **인공지능(AI)** 및 **데이터 기반 경제**의 핵심 원동력이 되는 **디지털 자산**.
- **규모·생성 주기:** 디지털 환경에서 생성되는 데이터가 **로그 규모로 방대**하고 **생성 주기도 짧다**. 수치·정형 데이터뿐 아니라 **문자·영상** 등 **비정형 데이터**를 모두 포함하는 **대규모 데이터**.
- **기술의 진화:** 단순 **저장**에 그치지 않고, **AI의 추론·지각 능력**을 실현하는 **연료** 역할. (Gartner 등: 생성형 AI·인사이트 엔진이 정형·비정형 데이터를 통합해 활용.)
- **한계 돌파:** 기존 시스템의 **수집·저장·분석 한계**를 **정보통신기술(ICT)** 의 발달로 극복한 결과물. 분산 저장(하둡 등), 스트리밍 처리(Kafka, Flink), 멀티모달·비정형 파이프라인이 그 예.
- **실시간 가치:** **매초 생성되는** 방대한 데이터를 **실시간으로 처리**하여 **즉각적인 의사결정**에 기여. (실시간 의사결정(Real-Time Decisioning): 스트리밍 데이터를 평가해 밀리초~초 단위로 자동 액션을 트리거.)

---

### 11.2 3V — Volume, Velocity, Variety (웹 그라운딩)

**3V**는 Gartner 애널리스트 **Doug Laney**가 2001년 Meta Group 연구 "3D Data Management: Controlling Data Volume, Velocity and Variety"에서 제안한 빅데이터의 세 가지 정의 속성이다. (TechTarget, Forbes 등에서 표준적으로 인용.)

| V | 영문 | 의미 | 한 줄 |
|---|------|------|--------|
| **Volume** | 규모 | **데이터의 양**. 수집·관리되는 데이터의 규모가 기존 DB·스프레드시트로는 감당하기 어려운 수준. | TB·PB 단위, 로그·센서·트랜잭션 누적. |
| **Velocity** | 속도 | **데이터가 생성·유입·처리되는 속도**. 얼마나 **빨리** 들어오고, **실시간**으로 분석·반영해야 하는가. | 스트리밍, 초당 이벤트, 배치 대비 실시간. |
| **Variety** | 다양성 | **데이터의 종류·형식·출처**의 다양성. 정형(테이블)·반정형(JSON)·비정형(텍스트·이미지·음성·영상)이 혼재. | 소스·포맷·스키마가 제각각. |

- **왜 3V인가:** 빅데이터 관리의 **도전**은 “양만 많은 것”이 아니라 **세 가지가 동시에 커지는 것**에서 온다. Volume·Velocity·Variety가 함께 확대될수록 분석적 가치와 기술적 난이도가 동시에 증가한다. (TechTarget, Brainforge 등.)
- **확장된 V:** 이후 **Veracity(진실성·품질)**, **Value(가치)** 등이 추가로 논의되기도 한다.

---

### 11.3 비정형 데이터와 AI·통찰 (웹 그라운딩)

- **비정형 데이터:** 문서, 이메일, 이미지, 영상 등 **고정 스키마가 없는** 데이터. 빅데이터에서 비중이 크고, **AI·생성형 AI**의 입력으로 핵심이 됨. (Gartner: 생성형 AI 사용 사례 대부분이 대량의 비정형 정보를 추출·정제·거버넌스하고 정형 파이프라인과 통합하는 것을 전제로 함.)
- **통찰 추출:** **Insight Engine** 개념 — 관련성 기반으로 데이터를 기술·발견·구성·분석하고, **적시에** 사업적 순간에 정보를 제공. 비정형(영상·문서)과 정형(스프레드시트·DB)을 모두 인덱싱·전처리해 쿼리·추출에 활용. (Gartner Glossary.)
- **데이터 중심 AI:** Gartner 등에서 강조하는 **Data-Centric AI** — 알고리즘·코드 개선보다 **데이터를 반복적으로 개선**해 AI 성능을 올리는 접근. AI가 텍스트·이미지·영상 등 **비정형 입력**에 점점 더 의존하므로, 비정형 데이터의 품질·메타데이터·파이프라인이 중요해진다.

---

### 11.4 실시간 처리와 즉각적 의사결정 (웹 그라운딩)

- **실시간 의사결정(Real-Time Decisioning):** 스트리밍 데이터를 **평가**하고, **규칙 또는 ML 모델**에 따라 **즉시 자동 액션**을 수행하는 능력. 인간 개입 없이 밀리초~초 단위로 결정·실행. (Confluent, Streamkap 등.)
- **흐름:** (1) **신호 발생**(이벤트) → (2) **로직 적용**(규칙/ML) → (3) **다운스트림 액션** 트리거. 과거 배치(12~72시간 지연)에서 **스트리밍·실시간**으로 전환.
- **구성요소:** (1) **수집(Ingestion)** — 스트리밍 이벤트 수신, (2) **처리(Processing)** — 데이터 처리·모델 적용, (3) **저장(Storage)** — 결과·상태 저장. (Redpanda + BigQuery, Kafka, Spark Structured Streaming 등.)
- **효과:** 시장 변화에 대한 **빠른 대응**, **운영 효율**(데이터 생성 시점에 처리), **실시간 개인화·사기 탐지** 등.

---

### 11.5 빅데이터 현상: 기술과 기법의 상호작용

- **단순한 “데이터 증가”가 아님:** 빅데이터 현상은 **데이터 양의 증가**만이 아니라, **기술(저장·분산·스트리밍)·기법(분석·ML·시각화)** 의 **상호작용**으로 이해해야 한다. “많다”를 어떻게 수집·저장·처리·활용할 것인가가 핵심.
- **내부 데이터 → 외부·비정형으로 확장:**  
  - **대부분의 기업**은 여전히 **내부 데이터(트랜잭션·ERP·CRM)** 분석에 집중한다.  
  - 한편 **소셜 미디어**, **멀티미디어**(영상·이미지·음성) 같은 **외부·비정형 데이터**로 **분석 영역을 확장**하는 추세다.  
  - 이에 따라 **Variety** 대응(정형·비정형 통합), **Velocity** 대응(실시간·배치 혼합), **Volume** 대응(분산·클라우드)이 함께 요구된다.

---

### 11.6 빅데이터 활용 예시: Smart Farm

#### 미국 Smart Farm

- **배경:** 땅이 넓은 미국에서는 농부들이 밭에 **온도·습도 센서**를 **비행기로 뿌려** 배포한다.
- **수집·전송:** 센서가 온도·습도를 측정해 **무선인터넷**으로 농부에게 전송하고, 농부는 **자기 방 안의 컴퓨터 스크린**을 통해 **실시간 정보**를 확인한다.
- **활용:** **물이 부족한 영역**만 식별 가능. 과거에는 넓은 밭 **전체**에 물을 뿌렸다면, 이제는 **물이 부족하다고 확인된 부분만** 선택적으로 물을 공급한다. → **Volume·Velocity·실시간 의사결정**의 대표 사례.

#### 국내 Smart Farm

- **역사:** 국내 스마트팜 기술 연구는 **1990년대 중반 이후** 본격화. **규모 유리 온실**을 구축해 **온도·습도** 등 몇 가지 **생육 환경**을 제어·자동화하는 **하드웨어 연구** 중심으로 시작.
- **2세대:** **소프트웨어 중심**의 2세대 스마트팜 기술이 등장하면서, 센서를 통한 제어 범위가 **재배 환경**을 넘어 **작물의 생육·생리 상태**까지 파악하는 수준으로 확대.
- **데이터 중심:** 식물의 **크기·색·형태**를 감지하는 센서가 수집한 **데이터**로 작물의 **품질·생산성**을 파악 → **데이터 중심의 생육 제어** 시대로 전환.

---

### 11.7 빅데이터 플랫폼: 수집·저장·처리·사용 (AWS 등)

빅데이터 플랫폼은 **수집 → 저장 → 처리·분석 → 사용·시각화**의 단계로 구성된다. 좋은 플랫폼을 구축하면 각 단계 수행이 수월해지고, **어느 속도에서든 다양한 데이터(정형~비정형)** 를 다룰 수 있다. (AWS 빅데이터 소개 등 참고.)

| 단계 | 내용 |
|------|------|
| **1. 수집** | **Raw 데이터**(트랜잭션, 웹 로그, 모바일 디바이스 등)를 수집. 다양한 **속도**와 **형식**(정형~비정형)을 수용할 수 있어야 함. |
| **2. 저장** | 처리 **전·후** 모두 데이터를 보관할 수 있는 **안전하고, 확장 가능하며, 내구력 있는** 저장장치 필요. 특정 요구에 따라 **전송용 임시 스토어**가 필요할 수 있음. |
| **3. 처리 및 분석** | 데이터가 **raw 상태**에서 **사용 가능한 형식**으로 변환되는 단계. **정렬·집계·조인**과 더불어 **고급 함수·알고리즘** 수행. 결과는 추가 처리용으로 저장하거나 **BI(비즈니스 인텔리전스)·데이터 시각화 도구**로 제공. |
| **4. 사용 및 시각화** | 빅데이터의 목적은 **데이터 자산**에서 **가치 높고 실행 가능한 통찰**을 얻는 것. **빠르고 쉽게** 데이터세트를 살펴볼 수 있는 **시각화 도구**를 통해 **이해관계자**에게 전달. |

### 11.8 빅데이터 작동 원리: 데이터 용량 단위

데이터 **용량**의 기본 단위부터 확장까지, **2의 10제곱(2¹⁰)** 배씩 커지는 계열로 이해한다.

- **비트(bit):** 데이터 용량의 **가장 작은 단위**. **0** 또는 **1**을 나타낸다.
- **바이트(byte):** 비트 **8개**를 하나로 묶은 단위. **1 byte = 8 bit**.
- **2¹⁰ 배씩 확장:** 1바이트가 **2¹⁰ = 1024**개 모이면 **킬로바이트(KB)**. 같은 방식으로 2¹⁰배씩 커지면서:

| 단위 | 약어 | 비고 |
|------|------|------|
| 킬로바이트 | KB | 2¹⁰ byte |
| 메가바이트 | MB | 2¹⁰ KB |
| 기가바이트 | GB | 2¹⁰ MB |
| 테라바이트 | TB | 2¹⁰ GB |
| 페타바이트 | PB | 2¹⁰ TB |
| 엑사바이트 | EB | 2¹⁰ PB |
| 제타바이트 | ZB | 2¹⁰ EB |

- 빅데이터의 **Volume**은 보통 **TB·PB** 단위 이상을 전제로 하며, 로그·센서·멀티미디어가 쌓일수록 **EB·ZB** 규모까지 논의된다.
