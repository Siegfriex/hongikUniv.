### 4강에서 다룬 내용 (요약)

- **7V·빅데이터:** 5V + **Volatility·Validity**, 비용·프라이버시·오판 등 부작용.
- **CRISP-DM** 6단계, **데이터사이언스 절차** 5단계(문제 정의→…→결과 적용) 및 **수집 기술**(FTP·API·크롤링·스크래핑, 공공 API·`robots.txt` 등).
- **데이터 거버넌스**, **Hadoop**(HDFS·MapReduce·YARN, 장단점, Uber 사례).
- 데이터 과학자 업무 시간 중 **데이터 준비(수집·정제·정리)** 비중이 매우 큼(설문·업계 관행과 연결).
- **Raw data**의 정성·정량 구분, 소셜 데이터의 비정형·수집·노이즈 이슈.
- **데이터 확인:** 독립/종속·변수 유형·데이터 타입, 단변수·이변수·다변수 탐색 도구(히스토그램, 산점도, 검정 등).
- **전처리:** 필터링(결측·틀린값·이상치), 변환(정규화·표준화·로그·이산화), 통합(식별자·단위·중복).
- **EDA:** Tukey, CDA vs EDA, 탐색 질문·과정·주제(저항성·잔차·재표현·시각화).
- **상관:** 피어슨 등, **상관 ≠ 인과**.

### 개념 간 관계도 (최종 점검)

`7V/문제정의 -> CRISP-DM/DS 절차 -> 수집(API·크롤링·데이터마켓) -> 준비/전처리(필터링·변환·통합) -> EDA(패턴 발견) -> 모델링(분류·회귀·군집·연관) -> 평가(지표/검증) -> 결과 적용(시각화·운영) -> 거버넌스/모니터링 -> 재학습`

- **앞 단계의 품질이 뒤 단계 성능을 결정**한다(garbage in, garbage out).
- **Hadoop/Spark/Flink**는 이 흐름의 “대규모 저장·처리 인프라” 레이어다.
- **의사결정 품질**은 모델 정확도 + 설명가능성 + 운영 안정성(드리프트 대응)으로 완성된다.

## 2. 빅데이터 7V·문제와 부작용

### 7V: 5V + Volatility + Validity

슬라이드는 **5V** (Volume, Variety, Velocity, Veracity, Value)에 **Volatility(휘발성)**, **Validity(유효성)** 를 더해 **7V**로 정리한다.

| V | 한글·요지 (슬라이드) |
|---|----------------------|
| **Volume** | 규모 |
| **Variety** | 다양성 |
| **Velocity** | 속도 |
| **Veracity** | 신뢰성 |
| **Value** | 가치(아래 참고) |
| **Volatility** | **휘발성** — 데이터가 **얼마나 오래 유효한지**, **언제까지 저장·분석**해야 하는지 |
| **Validity** | **유효성** — 분석 목적에 **부합하는지**, 데이터가 **얼마나 정확·깨끗한지**; **편향** 여부, **풀려는 문제와 실제 관련성** 검증 과정 |

**Value(가치)** 는 원래 의도한 분석 목적에 맞는지, 데이터 자체의 정확성·깨끗함, **편향**·**문제 적합성** 검증을 포함한다는 설명이 슬라이드에 함께 제시됨.

**출처:** Gupta, Yogesh Kumar & Surbhi Kumari, “A Study of Big Data Analytics using Apache Spark with Python and Scala,” *2020 3rd International Conference on Intelligent Sustainable Systems (ICISS)*, 471–478.

### 빅데이터: 문제와 부작용

- **데이터 폭증**에 따른 **데이터 관리 비용** 증가.
- **개인 프라이버시** 침해.
- **잘못된 분석**에 의한 **오판**.

**출처:** 김화종, 『데이터사이언스 개론』, 홍릉과학출판사, 2014.

## 3. CRISP-DM

**CRISP-DM** (*Cross Industry Standard Process for Data Mining*)은 데이터마이닝에서 널리 쓰이는 **공개 표준** 분석 모델이다.

- **1996년** EU **ESPRIT** 프로젝트 산출물.
- [Wikipedia — CRISP-DM](https://en.wikipedia.org/wiki/Cross-industry_standard_process_for_data_mining)

### 6단계 (슬라이드 요약)

| 단계 | 영문 | 내용 |
|------|------|------|
| 1 | **Business understanding** | 비즈니스 목표·데이터 분석 목표 수립, 업무 목적·데이터 마이닝 목표·프로젝트 계획, **초기에 어떤 데이터가 추출될지** 가설 |
| 2 | **Data understanding** | 초기 데이터 수집, 탐색, **품질 확인**, 특징·연관성 파악 — **EDA** |
| 3 | **Data preparation** | 분석 데이터셋 선택, **정제**, **통합**, 모델링 가능한 구조, **NaN**·**스케일링**, 필요 시 **파생 변수** |
| 4 | **Modeling** | 기법 선택, 테스트 계획, 모델 작성 — 변수 선택·알고리즘·학습·테스트(데이터셋 분리 등) |
| 5 | **Evaluation** | 결과·과정·**적용성** 평가; 테스트셋 **정확도**; 기술적(오차)·**비즈니스** 관점; **최종 모델**은 비즈니스 목표 부합이 중요 |
| 6 | **Deployment** | 모델이 고객 목표에 **충족**되는지, 운영에서 **품질 기준**·**모니터링**·유지보수·**종료 보고** |

## 4. 데이터사이언스 절차·수집·분석·적용

### 개념도·품질 프레임 (참고)

- 슬라이드에 **데이터사이언스 모델링 프로세스** 도식 인용: [Towards Data Science — modeling process](https://towardsdatascience.com/data-science-modeling-process-fa6e8e45bf02).
- 데이터 품질·지식 발견 과제 관련: Corrales, Ledezma, Corrales, “A conceptual framework for data quality in knowledge discovery tasks (FDQ-KDT),” *J. Comput.* 10.6 (2015): 396–405.

### 다섯 단계 (김화종, 2014 — 슬라이드)

1. **문제 정의** — 해결하려는 문제를 명확히.
2. **전략 수립** — 어떤 데이터를 어떻게 분석할지.
3. **데이터 수집** — 필요한 데이터 확보.
4. **데이터 분석** — 패턴, 분류, 예측 등 모델 구현.
5. **결과 적용** — 실제에 적용하고 성능 개선.

#### 1. 문제 정의 (상세)

- **도메인** 고민, **비즈니스 이해**를 바탕으로 문제 정의.
- **전문가·조직 구성원** 의견 수렴.
- 큰 문제를 한 번에 풀지 말고, **잘 알려진 단위 문제**로 나누기.

#### 2. 전략 수립 (상세)

- **관련 부서**, 데이터 **소유자**, **예산·기간**.
- 목표가 구체적일수록 수집이 효율적 — **핵심 데이터 확보**와 **사람·협력**이 성패를 좌우(도구만이 아님).
- **시간·비용·인력** 자원 고려.

#### 3. 데이터 수집 (상세)

- 수집에는 **비용**이 들며 **투자**로 볼 수 있음; 비용은 필요량·**프라이버시 침해 정도** 등에 따라 달라짐.
- **비용 vs 정확도 향상 이득** 균형.
- **잘못된 데이터 → 잘못된 결과** 필연.
- **IoT** 보급으로 **센서 데이터** 급증.
- **비정형·반정형**은 바로 쓰기 어려움 — 예: SNS 텍스트 **시간대별 단어 빈도** 등 **정형화** 노력.
- 정형으로 바꿀 때 **표준화된 형식**을 쓰면 이후 활용이 쉬움.
- **예측 모델 검증**에는 **정답(레이블) 데이터** 확보가 필수 — 수집 계획 시 **확보 가능 여부** 확인.

##### 수집 기술

| 기술 | 요지 |
|------|------|
| **FTP** | 서버–클라이언트 **파일 전송**; 웹페이지·스크립트·이미지 업·다운로드 등 |
| **API** | 두 소프트웨어가 **통신**하는 메커니즘 — **클라이언트** 요청·**서버** 응답 (예: 기상청 DB ↔ 날씨 앱). [GeeksforGeeks — What is an API?](https://www.geeksforgeeks.org/what-is-an-api/) |
| **크롤링(crawling)** | URL 접근·하이퍼링크 추적·색인·DB 저장 등 **자동 수집·분류**. 블로그·소셜 등 **대량** 수집. **무단 복제**는 지식재산권 이슈 가능 |

**Web Scraping vs Web Crawling (웹 그라운딩 보강)**

| 구분 | Web Crawling | Web Scraping |
|------|--------------|--------------|
| 핵심 목적 | 웹페이지를 **발견·탐색**하고 링크 구조를 따라 URL 목록/색인을 확장 | 수집된 페이지에서 **목표 필드만 추출**(제목, 가격, 리뷰, 표 등) |
| 대표 출력 | URL 목록, 페이지 메타데이터, 링크 그래프, 인덱스 후보 | 정형 데이터셋(CSV/JSON/DB 테이블) |
| 질문 형태 | “어떤 페이지가 존재하는가?” | “이 페이지에서 어떤 값이 필요한가?” |
| 예시 | 검색엔진의 URL discovery·크롤링 | 쇼핑몰 상품명/가격/리뷰 추출, 뉴스 제목/날짜 추출 |
| 실패 포인트 | 중복 URL 폭증, 무한 캘린더 링크, robots 차단 | DOM 변경으로 selector 깨짐, 동적 렌더링, 안티봇 |

- **관계:** 보통 `크롤링(발견) -> 스크래핑(추출)` 순서로 함께 쓰인다.  
  크롤링이 “어디를 볼지”를 만들고, 스크래핑이 “무엇을 가져올지”를 결정한다.
- **Google Search 관점:** Search는 `Crawling -> Indexing -> Serving` 3단계를 사용하며, 크롤링은 URL 발견·다운로드, 인덱싱은 내용 이해·DB 반영 단계다.

### 실무 파이프라인 (권장)

1. **목표 정의:** 필요한 필드·주기·품질 기준(정확도, 누락률) 명시.  
2. **접근 정책 확인:** `robots.txt`, 이용약관(Terms), 인증 필요 여부 확인.  
3. **수집 설계:**  
   - 크롤링: seed URL, 허용 도메인, 최대 깊이(depth), 중복 제거 규칙(canonicalize).  
   - 스크래핑: selector/XPath, 파싱 규칙, 동적 페이지(JS 렌더링) 대응.  
4. **요청 제어:** rate limit, 재시도(backoff), 타임아웃, 사용자 에이전트 식별.  
5. **정제·검증:** 타입 변환, 단위 통일, 결측/중복 처리, 스키마 검증.  
6. **저장·감사:** 원문(raw) + 정제본(curated) 분리 저장, 수집 시각/출처 URL 기록.

### 법·윤리·운영 체크리스트

- **공개 데이터라도 무조건 자유 이용은 아님:** 접근 가능성과 재사용 가능성은 다를 수 있어 저작권·약관·라이선스를 분리 확인.
- **개인정보 최소 수집:** 목적 외 수집 금지, 필요 시 비식별/마스킹, 보관 기간 정책 명확화.
- **서버 부하 최소화:** 짧은 시간 과도 요청 금지, `sleep`/큐 기반 스케줄링으로 트래픽 완화.
- **차단 신호 존중:** 403/429/5xx 증가 시 즉시 속도 낮추거나 중지.
- **재현성 확보:** 어떤 페이지를 어떤 규칙으로 언제 수집했는지 로그를 남겨 분석 신뢰성 확보.

### API 기반 수집 실습 흐름 (슬라이드 이미지 반영)

예시 과제: **2021년 1월 성북구 아파트 거래 건수 조회**

1. **엔드포인트 확인**
   - 예시 형태:  
     `https://api.odcloud.kr/api/RealEstateTradingSvc/v1/getRealEstateTradingCount`
2. **쿼리 파라미터 설정**
   - `page`, `perPage`, `returnType=JSON`
   - `cond[SEARCH_DATE::GTE]`, `cond[SEARCH_DATE::LTE]` (조회 기간)
   - `cond[REGION_CD::EQ]` (예: 성북구 코드)
   - `cond[DEAL_OBJ::EQ]` (거래 객체/유형)
   - `serviceKey` (인증키)
3. **요청 URL 생성/검증**
   - API 콘솔에서 생성된 URL을 브라우저로 열어 JSON이 내려오는지 확인.
   - 이 단계에서 이미지처럼 `currentCount`, `data`, `totalCount` 필드를 확인.
4. **코드 자동화**
   - 파라미터를 변수화해 월/지역을 반복 호출.
   - 응답 JSON에서 필요한 필드(예: `ALL_CNT`)만 추출해 저장.

### API 파라미터 시트 (이미지 기반 정리)

| 파라미터 | 의미 | 예시 |
|----------|------|------|
| `page` | 페이지 인덱스 | `1` |
| `perPage` | 페이지당 건수 | `10` |
| `returnType` | 응답 형식 | `JSON` |
| `cond[SEARCH_DATE::GTE]` | 조회 시작(포함) | `202101` |
| `cond[SEARCH_DATE::LTE]` | 조회 종료(포함) | `202102` |
| `cond[REGION_CD::EQ]` | 지역 코드 | `11290` (성북구 예시) |
| `cond[DEAL_OBJ::EQ]` | 거래 객체 코드 | `05` (슬라이드 예시) |
| `serviceKey` | 인증키 | 발급 키 |

> 슬라이드 캡처의 흐름: 입력 파라미터 지정 -> Request URL 생성 -> 응답 본문(JSON) 확인 -> 필요한 값(`ALL_CNT`) 추출.

### Python 예시 (수업용 최소 코드)

```python
import requests
import pandas as pd

endpoint = "https://api.odcloud.kr/api/RealEstateTradingSvc/v1/getRealEstateTradingCount"
params = {
    "page": 1,
    "perPage": 10,
    "returnType": "JSON",
    "cond[SEARCH_DATE::GTE]": "202101",
    "cond[SEARCH_DATE::LTE]": "202102",
    "cond[REGION_CD::EQ]": "11290",
    "cond[DEAL_OBJ::EQ]": "05",
    "serviceKey": "YOUR_SERVICE_KEY",
}

res = requests.get(endpoint, params=params, timeout=10)
res.raise_for_status()
payload = res.json()

rows = payload.get("data", [])
df = pd.DataFrame(rows)

# 슬라이드 예시의 핵심 필드
if not df.empty and "ALL_CNT" in df.columns:
    print("ALL_CNT:", df.loc[0, "ALL_CNT"])
print("currentCount:", payload.get("currentCount"), "totalCount:", payload.get("totalCount"))
```

### 페이징 전수 수집 패턴 (실무용)

```python
import math
import requests

endpoint = "https://api.odcloud.kr/api/RealEstateTradingSvc/v1/getRealEstateTradingCount"
base = {
    "perPage": 100,
    "returnType": "JSON",
    "cond[SEARCH_DATE::GTE]": "202101",
    "cond[SEARCH_DATE::LTE]": "202112",
    "cond[REGION_CD::EQ]": "11290",
    "cond[DEAL_OBJ::EQ]": "05",
    "serviceKey": "YOUR_SERVICE_KEY",
}

r0 = requests.get(endpoint, params={**base, "page": 1}, timeout=10).json()
total = int(r0.get("totalCount", 0))
pages = max(1, math.ceil(total / base["perPage"]))

all_rows = []
for page in range(1, pages + 1):
    r = requests.get(endpoint, params={**base, "page": page}, timeout=10)
    r.raise_for_status()
    all_rows.extend(r.json().get("data", []))
```

### 이미지 기반 인텔리전스 포인트

- API 문서 UI에서 값만 바꾸면 URL이 즉시 바뀌므로, **파라미터-결과 대응관계**를 빠르게 실험할 수 있음.
- `cond[...]` 파라미터는 인코딩되어 URL에 붙기 때문에, 코드에서는 dict 기반으로 관리하고 `requests`의 `params`를 쓰는 편이 안전함.
- 응답 페이징(`page`, `perPage`)과 `totalCount`를 함께 써서 **누락 없는 전수 수집** 루프를 작성해야 함.
- 수집 직후 `data` 스키마를 고정(열 이름, 타입)해두면 이후 전처리·분석 단계에서 오류가 크게 줄어듦.
- API가 안정적인 경우, HTML scraping보다 **재현성/유지보수성**이 높음.
- 슬라이드 코드에는 `eval(...)` 예시가 보이는데, 실무에서는 보안·안정성 때문에 `response.json()` 또는 `json.loads()` 사용이 권장됨.
- 월 단위 반복 수집 시 `SEARCH_DATE`를 문자열(`YYYYMM`)로 통일하고, 저장 시 날짜 타입으로 변환 규칙을 명시하는 것이 좋음.

**윤리·운영 (슬라이드)**

- API가 아니면 **`robots.txt`** 로 **크롤링 허용 여부** 확인 (`사이트/robots.txt`).
- 짧은 시간 **다수 요청**은 서버 부하·**디도스 유사** — `time.sleep()` 등으로 간격, **IP 차단** 사례 있음.
- **저작권**·이용 조건 확인.

**데이터 마켓·공공 데이터**

- 직접 수집보다 **외부 의뢰·구매**가 저렴·빠를 수 있음.
- 예: **Factual**(위치), **InfoChimps**, **Acxiom**(공공기록 가공·세그먼트 등), **Kaggle**.
- 공공: **data.gov**(미), **data.go.kr**(한).

### 데이터 소싱 전략 (직접 수집 vs API vs 데이터마켓)

| 방식 | 장점 | 리스크/주의 |
|------|------|-------------|
| **직접 수집(크롤링/스크래핑)** | 맞춤형 데이터 확보, 빠른 실험 | 유지보수 비용, 법/정책 이슈, 품질 편차 |
| **API 수집** | 구조화 응답(JSON), 문서화, 재현성 | 호출 한도, 인증/권한, 스키마 변경 |
| **데이터마켓/외부 구매** | 시간 단축, 대규모/전문 데이터 | 비용, 라이선스 제한, 도메인 적합성 검증 필요 |

- 실무에서는 세 가지를 혼합해 사용하며, 최종 선택 기준은 **비용·속도·품질·법적 리스크** 균형이다.
- 슬라이드의 일부 업체는 시점에 따라 서비스 상태가 달라질 수 있으므로, 과제/실무 적용 전 **현행 서비스 여부**를 재확인한다.

#### 4. 데이터 분석 (슬라이드)

- **기초 통계:** 평균·분산·분포.
- **클러스터링**, **연관규칙**, **분류**, **예측** 등.
- 방법 선택 시 **정확도 평가 기준**을 함께 설계; **실전 적용** 가능성도 검토.

### 웹 그라운딩 핵심 정의

- **데이터마이닝/분석의 목적:** 대규모 데이터에서 패턴과 유용한 정보를 찾아 **설명**하거나 **예측**하는 것(IBM).
- **클러스터링(비지도):** 레이블 없는 데이터를 유사성 기준으로 묶는 방법(k-means, 계층 군집 등).
- **연관규칙:** 변수/아이템 간 동시 발생 규칙을 찾는 방법(장바구니 분석 등).
- **분류/회귀:** 분류는 범주 예측, 회귀는 연속값 예측.

### 분석 태스크-알고리즘 매핑 (수업 정리용)

| 태스크 | 대표 알고리즘 | 대표 지표 |
|--------|----------------|-----------|
| 회귀(수치 예측) | Linear Regression, Random Forest Regressor, XGBoost | MAE, RMSE, MAPE |
| 분류(카테고리 판별) | Logistic Regression, SVM, Decision Tree, Neural Network | Accuracy, Precision, Recall, F1, ROC-AUC |
| 군집 | k-means, Hierarchical Clustering, DBSCAN | Silhouette, Davies-Bouldin |
| 연관규칙 | Apriori, FP-Growth | Support, Confidence, Lift |

- 슬라이드의 “기초통계 -> 군집 -> 연관 -> 분류 -> 예측” 흐름을 실습 설계의 기본 프레임으로 사용할 수 있음.

### 방법론: 실제로 어떻게 진행하는가 (단계별)

1. **문제 타입 확정**
   - 목표가 “구매 여부/등급”이면 **분류**, “매출/가격”이면 **회귀**, “고객군 자동 분리”면 **군집**, “동시 구매 패턴”이면 **연관규칙**.
2. **베이스라인 설정**
   - 분류: 다수 클래스 예측(majority class), 회귀: 평균 예측 모델부터 시작.
   - 고급 모델 성능은 반드시 베이스라인 대비 개선폭으로 판단.
3. **데이터 분할**
   - 일반 데이터: `train/valid/test` (예: 6:2:2).
   - 시계열 데이터: 과거->미래 순서 유지(랜덤 분할 금지).
4. **피처 엔지니어링**
   - 결측 처리, 범주형 인코딩, 스케일링, 로그 변환 등 전처리.
   - 누설 위험 변수(미래 정보, 결과를 직접 암시하는 컬럼) 제거.
5. **모델 후보 학습**
   - 간단한 모델 + 복잡한 모델을 함께 비교(예: Logistic vs XGBoost).
   - 하이퍼파라미터 탐색은 Grid/Random Search + 교차검증 사용.
6. **검증·선택**
   - 사전 정의한 핵심 지표 1~2개 + 보조 지표로 모델 선택.
   - 분류는 임계값(threshold) 조정까지 포함해 최종 성능 판단.
7. **에러 분석**
   - 오분류/대오차 샘플을 직접 확인해 데이터 문제인지 모델 문제인지 분리.
   - 특정 집단(지역/연령/상품군)에서 성능 편차가 큰지 확인.
8. **배포 전 점검**
   - 추론 시간, 비용, 결측 입력 처리, 장애 시 fallback 로직 체크.
   - 운영 모니터링 지표와 알람 임계값을 먼저 정한 뒤 배포.

### 태스크별 최소 절차 (Quick Recipe)

| 태스크 | 최소 절차 |
|--------|-----------|
| **분류** | 클래스 분포 확인 -> 기준 모델(Logistic) -> PR/F1/ROC-AUC 비교 -> 임계값 튜닝 |
| **회귀** | 타깃 분포/이상치 확인 -> 기준 모델(Linear) -> MAE/RMSE 비교 -> 잔차 분석 |
| **군집** | 스케일링 -> k 후보 탐색(엘보/실루엣) -> 군집 프로파일링 -> 비즈니스 해석 |
| **연관규칙** | 트랜잭션 포맷 변환 -> 최소 support/confidence 설정 -> lift 상위 규칙 검토 |

### 실패를 줄이는 실무 팁

- 성능이 안 나오면 알고리즘 교체보다 먼저 **데이터 품질/레이블 품질**을 점검.
- 불균형 분류에서 Accuracy만 보고 의사결정하지 않기.
- 모델 카드(데이터 기간, 버전, 지표, 한계, 금지 사용처)를 남겨 재현성 확보.

### 평가 기준을 먼저 정해야 하는 이유 (웹 그라운딩)

- 같은 모델도 **지표 선택**에 따라 결론이 달라진다.
- 클래스 불균형 문제에서 Accuracy만 보면 성능을 과대평가할 수 있어 `Precision/Recall/F1/ROC-AUC`를 함께 본다.
- 회귀는 오차 크기와 해석 단위에 맞춰 `MAE/RMSE/MAPE`를 선택한다.
- scikit-learn은 교차검증·그리드서치와 연계 가능한 `scoring` 체계를 제공해, 지표 기반 모델 선택을 표준화할 수 있다.

### 분석 모델 구현 시 체크리스트

- **목표-지표 정합성:** 예측 정확도만이 아니라 비즈니스 KPI(예: 리드타임, 비용절감)와 연결.
- **평가 분리:** 학습/검증/테스트 분리, 시계열 문제는 시간 누수(data leakage) 방지.
- **오류 비용 고려:** FP/FN 중 무엇이 더 치명적인지 반영해 임계값 설정.
- **설명 가능성:** 결과를 실무자가 이해·수용할 수 있는지(피처 중요도, 사례 설명) 점검.
- **배포 가능성:** 모델 정확도뿐 아니라 지연시간(latency), 추론비용, 운영 난이도까지 포함해 채택 여부를 판단.

#### C) 이미지의 Data Science 벤다이어그램 해석

- 데이터사이언스는 **Computer Science + Math & Statistics + Business/Domain Expertise**의 교차영역.
- 중앙의 **Machine Learning / Data Analysis**는 핵심 방법론이고,
- **Traditional Software** 역량은 실제 서비스 적용(배포·운영·자동화)에 필수.

#### D) 이 4강 노트에 맞춘 실전 적용 가이드

1. **분석 질문**부터 확정: “예측/분류/군집/연관규칙 중 무엇인가?”  
2. 질문에 맞는 **가벼운 베이스라인 모델** 먼저 실행(Linear/Logistic/Tree 등).  
3. 성능 부족 시 PCA, SVM, 앙상블, 신경망으로 확장.  
4. 최종 단계는 반드시 **시각화 도구(Tableau/Data Studio/Sheets)** 로 결과를 설명 가능하게 만든다.  
5. 운영을 고려하면 모델 성능뿐 아니라 **재현성(Jupyter+코드버전)·배포성(GCP 등)** 도 함께 점검한다.

### E) 도구가 데이터 기반 의사결정을 돕는 방식 (핵심)

의사결정은 보통 `데이터 -> 분석/모델 -> 해석 -> 실행안 -> 모니터링` 흐름으로 완성된다.
각 도구는 이 체인에서 맡는 역할이 다르며, **여러 도구를 연결할 때** 효과가 나온다.

| 단계 | 주로 쓰는 도구 | 무엇을 하는가 | 의사결정에 주는 가치 |
|------|----------------|---------------|----------------------|
| 데이터 준비 | pandas, NumPy, Python | 결측/이상치 처리, 집계, 피처 생성 | 잘못된 데이터로 인한 오판 감소 |
| 모델링 | scikit-learn, TensorFlow/Keras/PyTorch, R | 분류/회귀/군집/연관규칙 학습 | “무엇이 일어날지”를 정량 근거로 제시 |
| 평가/검증 | scikit-learn metrics, 교차검증, 통계 검정(R) | 정확도·재현율·오차·유의성 검토 | 잘못된 모델 채택 방지 |
| 전달/설명 | Tableau, Data Studio, Google Sheets, Jupyter | 대시보드·리포트·스토리텔링 | 비전문가도 실행 결정을 내릴 수 있음 |
| 운영/배포 | GCP 등 클라우드, 모니터링 도구 | 성능·드리프트 감시, 재학습 트리거 | 결정 품질을 장기적으로 유지 |

### F) "왜" 이 도구 구성이 필요한가

- **단일 도구만으로는 부족**: 모델이 좋아도 전달(시각화/리포트)이 약하면 실행되지 않는다.
- **재현성 확보**: Jupyter 실험 -> 코드화 -> 배포 환경 전환 흐름이 있어야 다음 달에도 같은 결론을 검증 가능.
- **리스크 통제**: 운영 중 데이터 분포가 바뀌면(data drift) 과거의 좋은 모델이 갑자기 나빠질 수 있어 모니터링 필수.
- **속도와 품질의 균형**: 초기엔 scikit-learn으로 빠르게 베이스라인, 복잡 패턴이 필요할 때만 딥러닝으로 확장.

### G) 의사결정 시나리오 예시 (수업 주제 연결)

1. **부동산 거래 건수 예측(회귀)**
   - 데이터: 월별 거래 건수, 지역 코드, 금리/계절성 변수.
   - 도구: pandas 전처리 -> scikit-learn 회귀 -> Tableau 시각화.
   - 의사결정: 특정 구의 다음 분기 거래 감소 예상 시, 마케팅/중개 인력 배치 선제 조정.

2. **고객 이탈 위험 분류(분류)**
   - 데이터: 최근 이용 빈도, 결제 이력, CS 이슈.
   - 도구: Logistic/Tree 기반 분류 + Precision/Recall 임계값 조정.
   - 의사결정: 고위험 고객군에 쿠폰·콜백 우선 배정(예산 효율 개선).

3. **상품 묶음 추천(연관규칙)**
   - 데이터: 장바구니 트랜잭션.
   - 도구: Apriori(FP-Growth)로 높은 Lift 규칙 추출.
   - 의사결정: 동시 구매 확률 높은 묶음 상품 기획/진열 변경.

### H) 도구 선택 의사결정 규칙 (실무용)

- **해석 가능성이 중요**(규제/설명 책임)하면: Linear/Logistic/Tree 우선.
- **정확도가 최우선**이고 비선형이 강하면: 앙상블/신경망 고려.
- **데이터가 작고 피처가 명확**하면: scikit-learn 전통 ML이 보통 효율적.
- **비정형 대용량(이미지/텍스트/음성)**이면: TensorFlow/Keras/PyTorch 계열이 적합.
- **조직 의사결정 전달**이 핵심이면: 모델보다 대시보드/지표 설계 품질이 성패를 좌우.

#### 5. 결과 적용 (슬라이드)

- **시각화**로 비전문가에게 설명.
- **알기 쉬운** 전달.
- 실무 적용 후 **피드백**으로 모델 **개선 루프**.

### 결과 적용 템플릿 (보고/배포 공통)

1. **문제·목표 KPI**: 무엇을 개선하려는지 한 줄로 명시.
2. **데이터 범위**: 기간/지역/대상, 제외 기준.
3. **모델 결과**: 핵심 지표 3개 이내.
4. **해석**: 왜 이런 결과가 나왔는지 피처·사례 중심 설명.
5. **실행안**: 당장 적용 가능한 액션 1~3개.
6. **모니터링 계획**: 주기, 임계값, 재학습 조건.

### 운영 적용(Deployment) 관점 보강

- **모니터링:** 예측 성능(정확도/오차) + 데이터 품질(결측률/분포 이동) 동시 모니터링.
- **드리프트 대응:** 입력 분포 변화(**data drift**)와 학습-서빙 분포 차이(**data skew**)를 구분해 감시하고, 재학습 주기/트리거를 정의.
- **실패 대비:** 규칙 기반 백업 로직, 모델 장애 시 롤백 경로 확보.
- **커뮤니케이션:** 대시보드/리포트로 의사결정자·현업·개발팀이 같은 지표를 보게 설계.

### 종합 의사결정 플로우 (실무 템플릿)

1. **질문 정의:** “무엇을 예측/판단할 것인가?” (예: 수요, 이탈, 가격)
2. **성공 지표 합의:** 비즈니스 KPI + 모델 지표(예: F1, RMSE)
3. **데이터 계약:** 수집 범위, 갱신 주기, 품질 기준, 책임자
4. **모델 실험:** 베이스라인 -> 개선 모델 -> 에러 분석
5. **배포 판단:** 성능, 지연시간, 비용, 설명가능성, 리스크 점검
6. **운영 모니터링:** 성능 저하/드리프트 알람, 재학습 트리거
7. **피드백 루프:** 현업 결과 반영해 정책·모델 업데이트

## 5. 데이터 거버넌스

**데이터 거버넌스(data governance):** 데이터 **가공·활용** 전 과정에 필요한 **정책·보안·프로세스·표준·관리 체계** 등 일련의 업무.

## 6. 빅데이터 처리 기술: Hadoop

### 개요

- **Hadoop:** 대용량 데이터 **분산 처리** **자바** 기반 **오픈소스** 프레임워크.
- **정형·비정형**(사진·영상 등) 처리에 활용되는 **에코시스템**; 빅데이터 **사실상 표준** 플랫폼으로 자리.
- **2005년** **Doug Cutting** 이 구글 논문의 **GFS**, **MapReduce** 를 구현한 결과로 알려짐; 이름은 아들의 노란 코끼리 **인형 이름**에서 유래(슬라이드).
- Facebook·Yahoo 등 **대규모 노드** 클러스터 사례, **SK** 2008년 도입 등 언급.

**공식:** [https://hadoop.apache.org/](https://hadoop.apache.org/)

### 탄생 배경과 핵심 아이디어 (왜 Hadoop인가)

- 단일 서버로 감당하기 어려운 데이터 규모(TB~PB)를 **여러 대의 범용 서버**로 나눠 처리하려는 목적.
- 핵심 철학은 **Scale-out**(큰 서버 1대 대신, 보통 서버 N대 확장) + **데이터 지역성(Data Locality)**.
- 데이터 지역성: “계산을 데이터가 있는 곳으로 보낸다”는 개념으로, 네트워크 전송 비용을 줄여 처리량을 높임.

### 구조·동작

- 데이터가 **쪼개져** **파티션** 단위로 **클러스터 노드**에 **분산 저장**.
- **클러스터:** 네트워크로 연결된 컴퓨터 집합이 하나처럼 동작.
- 분석 도구가 **각 노드 데이터**를 **병렬** 처리 → 속도.
- 슬라이드 서술: **저장된 곳에서 분석**하여 **별도 ETL 이동**이 없을 수 있음(맥락에 따라 다름).
- 그 외 프레임워크: **Storm**, **Spark**, **Flink** 등.

### MapReduce 처리 흐름 (구체)

1. **Input Split**: 원본 데이터를 블록/스플릿으로 분할.
2. **Map**: 각 노드에서 `(key, value)` 형태의 중간 결과 생성.
3. **Shuffle & Sort**: 같은 key를 모아 정렬·재분배(네트워크 비용이 큰 구간).
4. **Reduce**: key별 집계/결합 결과 생성.
5. **Output**: HDFS 등에 결과 저장.

- 요점: 병렬 처리의 속도 이점은 크지만, **Shuffle 구간**과 **디스크 I/O**가 병목이 될 수 있음.

### 구성 요소

| 구성 요소 | 역할 |
|-----------|------|
| **HDFS** | 분산 파일 시스템 — **높은 처리량** 접근 |
| **MapReduce** | **map**·**reduce** 로 분산 처리 |
| **YARN** | 자원·스케줄링 — CPU·RAM 할당, 다수 작업 관리 |

참고: [DataFlair — Hadoop for data science](https://data-flair.training/blogs/hadoop-for-data-science), [ProjectPro — Hadoop cluster](https://www.projectpro.io/article/hadoop-cluster-overview-what-it-is-and-how-to-setup-one/356).

### 구성 요소 상세 (실무 관점)

- **HDFS**
  - 대용량 파일을 블록 단위로 분할해 여러 DataNode에 저장.
  - 장애 대응을 위해 복제(Replication) 기반 내구성을 확보.
  - 특징: 낮은 지연(latency)보다 **높은 처리량(throughput)** 에 최적화.
- **MapReduce**
  - 대용량 배치 처리에 강점.
  - 작업 시작/종료 오버헤드가 있어 짧은 인터랙티브 질의엔 비효율일 수 있음.
- **YARN**
  - ResourceManager/NodeManager 기반으로 클러스터 자원과 작업 스케줄을 관리.
  - MapReduce뿐 아니라 다양한 엔진(Spark 등)도 YARN 위에서 실행 가능.

### 장점 (슬라이드)

- **저렴한 PC**·**리눅스** 등으로 구축 가능.
- **고가 DBMS** 없이도 대용량 처리.
- **확장성** — 데이터 증가 시 **하드웨어 추가**로 용량 확장.
- **형식에 구애받지 않음** — 텍스트·오디오·동영상·수치 등.
- **저장 효율**·**비용** 면에서 전통 DB 대비 이점이 입증되었다는 서술.

### 단점 (슬라이드)

- **분산 구조**라 전체 상관관계 분석이 “불가능”하다기보다, **조인/셔플 비용**과 지연이 커져 비효율적일 수 있음.
- **실행 지연**이 길 수 있음.
- **배치** 중심 — 새 데이터 유입 시 **전체 재작업** 등으로 분석 시간 증가 가능 → **실시간**에는 한계.

### 언제 적합/부적합한가 (의사결정 관점)

| 구분 | 적합한 경우 | 부적합한 경우 |
|------|-------------|---------------|
| 워크로드 | 대규모 로그 ETL, 일/주 단위 배치 집계, 데이터 레이크 저장 | 실시간 응답 API, 초저지연 대화형 분석, 소규모 데이터 단건 질의 |
| 데이터 성격 | 파일 기반 대용량 정형·반정형·비정형 | 작은 테이블에 대한 빠른 트랜잭션 처리(OLTP) |
| 운영 목표 | 비용 효율적 확장, 장애 허용 분산처리 | 즉시성/인터랙티브성이 핵심인 서비스 |

### Spark·Flink·Storm과의 관계 (짧은 비교)

- **Hadoop(MapReduce):** 견고한 배치 처리 중심.
- **Spark:** 메모리 중심 처리로 반복 연산/대화형 분석에 강함.
- **Flink/Storm:** 스트리밍(실시간) 처리에 강함.
- 실무에선 “HDFS 저장 + Spark/Flink 처리”처럼 **혼합 아키텍처**가 흔함.

### 관련 개념 그라운딩 (핵심 용어 정리)

| 개념 | 설명 | 실무 포인트 |
|------|------|-------------|
| **NameNode** | HDFS 메타데이터(파일 이름공간, 블록 매핑) 관리 | 단일 장애점 이슈가 있어 HA 구성이 중요 |
| **DataNode** | 실제 블록 데이터를 저장하는 노드 | 장애 시 블록 복제를 통해 가용성 유지 |
| **Block** | HDFS가 파일을 나누어 저장하는 단위 | 큰 파일 순차 읽기에 유리 |
| **Replication Factor** | 각 블록의 복제 개수 | 높이면 내구성↑, 저장비용↑ |
| **Rack Awareness** | 복제본을 랙 단위로 분산 배치 | 랙 장애 대비 + 네트워크 효율 개선 |
| **Container (YARN)** | 애플리케이션에 할당되는 실행 자원 단위 | 메모리/CPU 할당 정책이 성능 좌우 |
| **Scheduler** | 클러스터 자원 할당 정책(예: Capacity/Fair) | 다중 팀/다중 작업 환경에서 공정성·SLA 관리 |
| **Data Locality** | 데이터가 있는 노드 근처에서 연산 수행 | 네트워크 병목 완화, 처리량 향상 |

### 자주 생기는 오해 정리

- **“Hadoop이면 ETL이 필요 없다”**  
  -> 완전한 무-ETL이 아니라, 데이터 이동을 줄일 수 있다는 의미가 더 정확함.
- **“Hadoop은 실시간 처리가 불가능하다”**  
  -> MapReduce 자체는 배치 중심이지만, Hadoop 생태계에서 Spark/Flink/YARN 조합으로 준실시간·스트리밍 처리가 가능.
- **“분산이면 무조건 빠르다”**  
  -> Shuffle, 직렬화, 디스크 I/O, 작은 파일 과다(small files) 문제로 오히려 느려질 수 있음.
- **“복제 수를 높이면 항상 좋다”**  
  -> 내구성은 좋아지지만 저장비용·네트워크 복제 비용도 함께 증가.

### 적용 예: Uber (슬라이드)

우버 사례는 “대규모 수요·공급 데이터를 실시간에 가깝게 반영해 운영 의사결정을 자동화”하는 전형으로 소개된다.

- **확장 맥락:** 2009년 샌프란시스코 시작 후 글로벌 주요 도시로 확장(슬라이드 서술 기준).  
  도시별 운전자·승객·운행 로그가 누적되며 대규모 데이터 인프라가 필요해짐.
- **즉시 매칭:** 승객 호출 시, 위치·가용 상태·예상 도착시간(ETA) 등을 고려해 **적합 운전자**를 연결.
- **Dynamic Pricing:** 거리만이 아니라 **교통 혼잡, 날씨, 가용 운전자 수, 지역 수요 변화**를 함께 반영해 요금을 조정.
- **수요·공급 균형:** 운행 기록을 지속적으로 저장/분석해 시간대·지역별 수요를 예측하고, 운전자 배치 전략에 반영.
- **서지 프라이싱(surge pricing):** 수요 급증·공급 부족 상황에서 가변 가격을 적용해 배차 안정성을 확보하려는 메커니즘.
- **평가 시스템:** 운전자/탑승자 상호 평가 데이터로 신뢰·품질 관리를 수행하고, 매칭 의사결정의 보조 신호로 활용.

#### 우버 사례를 하둡 관점으로 읽는 법

1. **저장:** 도시/시간대별 대용량 로그를 분산 저장(HDFS 계열).
2. **처리:** 배치 분석(MapReduce/Spark)으로 수요 패턴·요금 정책 파라미터 추정.
3. **운영:** 스트리밍/온라인 시스템에서 현재 호출에 대한 매칭·요금 의사결정 수행.
4. **피드백:** 실제 운행/평가 결과를 다시 저장해 모델·정책을 주기적으로 업데이트.

> 정리: 하둡은 “즉시 요금 계산기” 하나라기보다, 우버 같은 서비스의 **대규모 데이터 저장·배치 분석 기반**을 담당하고, 실시간 의사결정 엔진과 결합되어 전체 플랫폼 성능을 만든다.

## 8. Raw Data: 정성·정량

### 정성 데이터 (Qualitative Data)

- **성질(Quality)·상태**를 나타내며, 숫자가 아닌 **언어·문자·이미지** 등으로 표현되는 데이터.
- **주관적 해석:** 연구자·분석가 해석에 따라 의미가 달라질 수 있음.
- **비정형성:** 일정 규격이 없어 전처리(텍스트 마이닝 등)가 복잡함.
- **심층 이해:** “이유”나 “맥락” 파악에 사용.
- **예:** 인터뷰, 고객 리뷰(텍스트), SNS 사진, 설문 주관식.

### 정량 데이터 (Quantitative Data)

- **양(Quantity)** 을 측정해 수치·양으로 표현할 수 있는 데이터.
- **객관적 측정:** 자·저울·시계 등 표준화된 도구로 측정 가능.
- **통계 분석:** 평균·분산·상관 등 수학적 계산이 바로 가능.
- **정형성:** 주로 표(Table)·DB 숫자 필드.
- **예:** 매출, 온도, 시험 점수, 방문 횟수, 키·몸무게.

### 정성 vs 정량 예시 (슬라이드 표)

| Qualitative | Quantitative |
|-------------|--------------|
| Interview recordings | Tables from databases |
| Transcripts, social media | Survey scales |
| Videos | Employee performance data |

## 9. 소셜 미디어 Raw Data의 어려움

1. **Unstructured raw data:** 분석이 어렵고, 문맥 파악이 힘들며 노이즈가 많음.
2. **수집 난이도:** Twitter·YouTube 등 일부 플랫폼 외에는 수집이 어렵고, **API 정책 변화**(예: X/Twitter 유료화)로 부담이 커질 수 있음.
3. **유용성:** 많은 데이터가 쓸모없을 수 있으며, **유의미한 패턴**을 찾으려면 불용어 제거·형태소 분석 등이 필요함.

## 11. 데이터 확인: 이변수 분석

### 이변수(Bivariate) 그래프·분석 (변수 조합별)

| 조합 | 방법 |
|------|------|
| **연속형–연속형** | Scatter(산점도), 상관관계 분석 |
| **범주형–범주형** | 빈도표, 100% 누적 막대, **카이제곱 독립성 검정**(두 변수 독립 여부) |
| **범주형–연속형** | 범주별 히스토그램, 누적 막대, Box plot · 범주 2개: **T-test / Z-test** · 범주 3개 이상: **ANOVA** |

### 예시 (연속형–연속형)

- **가설:** SNS 광고비를 많이 쓸수록 신규 가입자가 늘 것이다.
- **데이터:** 최근 24개월.
- **X:** 월간 SNS 광고 집행비(만원, 연속형).
- **Y:** 월간 신규 앱 가입자 수(명, 연속형).

### 예시 (범주형–범주형)

- **주제:** 성별에 따른 스마트폰 브랜드 선호 — **카이제곱 독립성 검정**.
- **H0:** 성별과 브랜드 선호는 **독립이다**(성별에 따른 차이 없음).
- **H1:** 성별과 브랜드 선호는 **독립이 아니다**(차이가 있다).

### 예시 (연속형–범주형)

- **주제:** 학력 수준에 따른 월평균 소득.
- 범주가 3개 이상(고졸/대졸/석사/박사)이면 **ANOVA** · 범주가 2개면 **T-검정**.
- **H0:** 모든 학력 그룹 간 **평균 소득 차이 없음**.
- **H1:** **적어도 한 그룹**은 다른 그룹과 평균 소득이 다름.

## 13. 데이터 전처리 개요

### 정의

- 수집 데이터는 **불완전·오염·단위 불일치** 등 다양한 문제를 포함할 수 있음 → **데이터 품질 검증** 필요.
- 분석·모델링에 맞게 **형식을 바꾸는** 작업도 포함.
- **분석하기 좋게 데이터를 고치는 모든 작업**을 **전처리(Preprocessing)** 라고 함.
- 오류를 걸러내고 깨끗하게 바꾸는 것을 **데이터 정제(cleaning)** 라고 부르기도 함.

### 상태·가치 점검 질문 (슬라이드)

- 중간에 데이터가 **빠져** 있는지? **틀린 값**이 있는지?
- **단위**가 섞였는지? (inch vs cm 등)
- 처리하기 **좋은 형식**인지? **새로 가공**해야 하는지?
- **범주형**이 문자로만 있어 숫자 인코딩이 필요한지?

## 15. 필터링: 결측치·틀린값·이상치

### 결측치 (Missing value)

| 대응 | 설명 |
|------|------|
| **삭제** | 결측이 있는 행·열 제거 — 비중이 높으면 원인·모델 타당성 검토 |
| **대체** | 평균·중위수·인접값, 회귀로 예측값 등 |
| **NA 표시 후 이송** | 예: 직업란 공란이 많으면 일단 `NA`로 두고 분석 단계에서 처리 |

### 틀린값 (Invalid data)

- 결측은 찾기 쉬우나 **틀린값은 발견이 어려움.**
- **삭제·대체·분석 단계로 이월** 등.
- 예: 숫자여야 할 곳에 문자열, **키 3.7 m** (명백한 입력 오류).

### 이상치 (Outlier) vs 틀린값

- 일반 범위를 벗난 **특이값**이 이상치.
- **틀린값과 다름:** 예) 키 **3.7 m** = 틀린값, **2.1 m** = 이상치(극단 키)일 수 있음.
- 슬라이드: **이상치 검출·처리의 상당 부분은 전처리가 아니라 데이터 분석 단계**(Anomaly detection, Outlier detection 등)로 넘길 수 있음.

### 이상치 발견

- **육안 관찰**, **통계량**(평균·중앙값·최빈값·범위·표준편차·사분위수, 평균 vs 중앙값, 평균±3σ 등).
- **시각화:** PDF, 히스토그램, 시계열, **워드클라우드(텍스트)**, **박스플롯**(outer fence 밖).
- **머신러닝:** 예) k-means.
- **통계 검정:** 예) Grubbs’ test.

### 이상치·틀린값 원인 (슬라이드)

- Data entry errors, Measurement errors, Experimental errors, Intentional errors(주량·흡연 등), Data processing errors, Sampling errors(예: 운동선수 키에 농구선수 과다 포함).

**출처:** Analytics Vidhya 가이드 등.

## 16. 데이터 변환: 이산화·정규화·표준화·로그

### 이산화 (Binning)

- 수치를 **범주**로 변환 — 나이를 10대·20대…, 소득을 고·중·저소득층 등.
- 히스토그램·클러스터링 등에 활용.

### 정규화 (Normalization) — 일반

- 여러 수치 변수의 **스케일이 다를 때** 비교·학습을 위해 **같은 범위**(예: 0~1, -1~1)로 맞춤.
- 예: A과목 만점 10, B과목 만점 50 → 절대 점수 비교 어려움 → **7/10=0.7**, **30/50=0.6** 처럼 스케일 맞춰 비교.

| 방법 | 요지 |
|------|------|
| **MaxAbs** | 절댓값 최대로 나눔 → 대략 -1~1 |
| **Min-Max** | 최소→0, 최대→1 매핑 → 0~1 |

### 기계학습 맥락 (경사 하강법)

- 한 변수는 0~1, 다른 변수는 0~1,000,000이면 **gradient 스케일이 달라** 업데이트가 불안정할 수 있음(슬라이드 직관).

### 표준화 (Standardization)

- **정규분포 가정** 하에 평균·표준편차 반영 — **Z-score**  
  \[
  z = \frac{x - \mu}{\sigma}
  \]
- **예:** 두 과목 모두 만점 100, 학급 평균 60으로 같으나 A는 표준편차 20, B는 5 → 같은 원점수 85라도 **상대적 난이도**가 다름. B에서 90점은 더 “어려운” 과목에서의 고득점일 수 있음 → 평균 0·표준편차 1로 환산해 비교(슬라이드의 학생 a/b 예).
- **활용:** kNN, SVM, 신경망 등에서 유용(슬라이드).

### 로그 변환

- **한쪽으로 치우친(skewed) 분포**, 값의 범위가 수만 배 차이 날 때 **압축**해 파악하기 쉽게 함(10, 100, 1000…).

## 17. 데이터 통합

- 출처는 다르지만 **연관된 데이터**를 하나로 결합.
- 동일 실체가 중복 입력될 수 있으므로 **중복 검출**, **단위 통일**(파운드↔kg, inch↔cm, 시간대 등).
- 데이터 과학자 작업 중 **60~70%** 가 품질 관리·가공에 해당하고, 그중 상당 부분이 **여러 세트 연결(통합)** (슬라이드 서술).
- **통합의 핵심:** **유일 식별자(unified identifier)** 가 있는지 — 있으면 이를로 중복 제거·한 집합으로 통합.

## 18. 전처리 예시: 와인 소비·질환 사망률

**데이터(슬라이드):** 여러 국가의 **와인 소비**와 **질환별 사망률** 관계 (C. Shah, 2020).

| 변수 | 의미(요약) |
|------|------------|
| Country | 국가명 |
| Alcohol | 1인당 와인 소비(L 등) |
| Deaths | 알코올 관련 사망(10만 명당) |
| Heart | 심장질환 사망(10만 명당) |
| Liver | 간질환 사망(10만 명당) |

**전처리 단계(슬라이드):**

- **노이즈:** Alcohol, death 수치의 **음수 → 양수**로 수정(smooth noisy data).
- **결측:** **평균값** 대체 등.
- **추가 데이터(인도):** 주(state) 평균으로 alcohol·Heart 계산, 나머지는 다른 값들의 평균 등으로 보완.
- **데이터 통합:** 위 과정과 결합.
- **데이터 축소:** 불필요한 소수 자릿수 정리, 분석에 불필요한 열 제거.
- **이산화:** Alcohol를 구간별 범주로 — 예) [0,1)→0, [1,2)→1, [2,5)→2, [5,∞)→3.

## 19. 데이터 탐색과 EDA

### 정의

- 수집 데이터가 분석에 **적절한지** 보는 과정.
- 본격 분석 전 **전체 특성** 파악.
- **탐색적 데이터 분석(Exploratory Data Analysis, EDA)**.

### Tukey (1977)

- 미국 벨 연구소 **John W. Tukey** 의 저서 제목이 EDA 방법론으로 정착.
- 기존 통계가 가설 검정 등에 치우쳐 **자료 본연의 의미** 탐색에 한계 → **주어진 자료만으로도** 정보를 찾을 수 있도록 탐색 기법 개발.

### CDA vs EDA

- **확증적 분석(Confirmatory Data Analysis, CDA):** 통계를 **가설 검증** 도구로 — 예: 직업·소득 상관을 **검증**하려는 목적에 자료를 맞춤.
- **EDA:** 한 가지 목적만 붙잡지 말고 **이리저리 살펴보고**, 시각화로 **여러 관점**에서 탐색.

(슬라이드: aliencoder.tistory.com, sebastiz.github.io 등 참고)

## 20. EDA 필요성·과정·주제

### 데이터 탐색을 위한 질문 (필드 케이디, 2018 — 슬라이드 요지)

- 데이터셋 **크기**, **전체 vs 일부** 샘플인지, **모집단 대표성**.
- 이상치·잡음, **임의 가공** 데이터 포함 여부.
- **식별자** 존재·중복·병합 시 동질성.
- **결측** 비율과 이유 등.

### EDA 필요성

- 분포·값 검토로 현상 이해·**잠재 문제** 발견 → 수집·분석 방향 결정.
- 여러 각도에서 **패턴** 발견 → 가설 **수정·신설**.

### EDA 과정 (4단계, 슬라이드)

1. 분석 목적·**변수** 확인, 변수명·설명 유무.
2. 데이터 **전체 스캔** — `head`/`tail`, 이상치·결측 등.
3. **개별 속성** 값이 예상 범위·분포인지, 이유 파악.
4. **속성 간 관계** — 상관·시각화로 개별 관찰에서 못 본 패턴.

**출처:** [eda-ai-lab.tistory.com](https://eda-ai-lab.tistory.com/13)

### EDA의 주제 (슬라이드)

1. **저항성(Resistance):** 이상치·결측·틀린값에 덜 민감한 통계량 — 예) 평균 대신 **중위수**.
2. **잔차 해석:** 값이 “흐름”에서 얼마나 벗어났는지 — 크게 벗어난 이유 탐구.
3. **재표현(Data re-expression):** 로그·제곱근·역수 등으로 척도 변환, 정규성·대칭성 확보.
4. **현시성(Graphic presentation):** stem-leaf, box plot, scatter plot 등 **시각화**.

## 21. 데이터 분포: 산포도와 상관계수

- **산포도(산점도):** 두 연속 변수 관계 시각화(이훈영, 『연구조사방법론』, 청람, 2012 등 슬라이드 출처).

### 상관계수

- 두 확률변수 **관련성** 파악.
- **피어슨·스피어만·켄달** 등 — 흔히 “상관계수”는 **피어슨**.
- 계수가 크면 **함께 변하는 정도가 큼**을 의미하나, **인과를 의미하지 않음** — **교란 변수 C** 가 A·B를 동시에 움직이거나, 방향이 반대(B가 A의 원인)일 수 있음.
